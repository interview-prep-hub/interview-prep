## Quick revision
- `class` defaults to private members and private inheritance; `struct` defaults to public. Otherwise identical.
- Construction: virtual bases, direct bases, members in **declaration order** (not initializer-list order), then the constructor body. Destruction is the exact reverse.
- Copy constructor creates a new object (`T b = a;`, pass or return by value); copy assignment overwrites an existing one (`b = a;`). The compiler's copy is member-wise: **shallow** for raw owning pointers, ending in a double free.
- Rule of 3: destructor, copy constructor, copy assignment travel together. Rule of 5: add move constructor and move assignment. Rule of 0: use RAII members and write none.
- `explicit` on single-argument constructors blocks surprise conversions. Static members belong to the class (static functions have no `this`). `friend` grants private access; not inherited, transitive or mutual.
- `operator<<` must be a non-member (the stream is the left operand); `=`, `[]`, `()` and `->` must be members.
- Runtime polymorphism needs a **virtual** function called through a **pointer or reference**. Calls on objects by value bind at compile time.
- Each polymorphic class has a **vtable** of function pointers; each object carries a hidden **vptr** to it. A virtual call loads the vptr, indexes the table, calls indirectly.
- Constructors cannot be virtual, and inside constructors and destructors virtual calls do not reach derived overrides. A base with virtual functions needs a **virtual destructor**, or `delete basePtr` is undefined behavior.
- A pure virtual function (`= 0`) makes a class abstract; an "interface" is pure virtuals plus a virtual destructor. `override` turns signature mismatches into compile errors; `final` blocks further overriding or inheritance.
- **Slicing**: copying a derived object into a base object by value drops the derived part and its overrides.
- **Diamond**: without `virtual` inheritance the shared base exists twice; with it, once, constructed by the most-derived class.
- **Name hiding**: a derived function hides every base function with the same name; `using Base::f;` restores them.
- Templates are instantiated per type at compile time and live in headers; `dynamic_cast` checks types at run time using RTTI.

## 1. Classes, structs and access

```cpp
class BankAccount {                      // members are private by default
public:
    explicit BankAccount(std::string owner, double balance = 0)
        : owner_(std::move(owner)), balance_(balance) {}
    void deposit(double amount) {
        if (amount <= 0) throw std::invalid_argument("amount must be positive");
        balance_ += amount;              // the class protects its invariant
    }
    double balance() const { return balance_; }
protected:                               // also visible to derived classes
    void log(const std::string& msg) const { std::cout << owner_ << ": " << msg << '\n'; }

private:                                 // this class and its friends only
    std::string owner_;
    double balance_;
};

struct Point { int x = 0; int y = 0; };  // public by default: plain data
```

Access control is per class, not per object: a member function may read another `BankAccount`'s private fields, which is how copy constructors work. Convention: `struct` for passive data, `class` when there is an invariant to protect.

## 2. Constructors

```cpp
class User {
public:
    User() : User("guest", 0) {}                                    // default, delegating (C++11)
    User(std::string name, int age)                                 // parameterized
        : name_(std::move(name)), age_(age) {}                      // member initializer list
    explicit User(std::string name) : User(std::move(name), 0) {}   // explicit: no implicit conversion
    // copy and move constructors are generated by the compiler (Rule of 0)
private:
    std::string name_;
    int age_;
};

void greet(const User& u);

User a;                         // default
User b("Sara", 22);             // parameterized
User c = b;                     // copy constructor
User d = std::move(b);          // move constructor
greet(User("Ali"));             // OK: explicit construction
// greet(std::string("Ali"));   // error: the one-argument constructor is explicit
```

- **Why initializer lists:** members are constructed before the body runs. Assigning in the body means default-construct, then assign, and it is impossible for `const` members, references and members without a default constructor.
- **Order trap:** members initialize in declaration order whatever the list says. `-Wall` includes `-Wreorder`, which warns about it.

```cpp
class Broken {
    int* data_;     // declared first, so initialized first...
    int size_;
public:
    explicit Broken(int n) : size_(n), data_(new int[size_]) {}   // ...reading size_ before it is set
};
```

- The compiler generates a default constructor only if you declare no constructor at all (`User() = default;` brings it back). Make single-argument constructors `explicit` unless the conversion is natural, like `std::string` from `const char*`.

## 3. Destructors and construction/destruction order

```cpp
#include <iostream>

struct Member {
    const char* name;
    explicit Member(const char* n) : name(n) { std::cout << "Member " << name << '\n'; }
    ~Member() { std::cout << "~Member " << name << '\n'; }
};

struct Base {
    Base() { std::cout << "Base\n"; }
    virtual ~Base() { std::cout << "~Base\n"; }
};

struct Derived : Base {
    Member a{"a"};
    Member b{"b"};
    Derived() { std::cout << "Derived\n"; }
    ~Derived() override { std::cout << "~Derived\n"; }
};

int main() { Derived d; }
// Prints: Base, Member a, Member b, Derived, then ~Derived, ~Member b, ~Member a, ~Base
```

- Locals are destroyed in reverse order of construction, array elements from last to first. Heap objects die only when deleted (by you or a smart pointer).
- Temporaries die at the end of the full expression, unless bound to a `const&` (or `&&`) local, which extends their life.
- Globals and statics are built before `main` (the order across files is unspecified: the "static initialization order fiasco") and destroyed after `main` returns, in reverse.

## 4. Copying: constructor vs assignment, shallow vs deep

```cpp
User a("Sara", 22);
User b = a;      // copy CONSTRUCTOR: b is being created (same as User b(a);)
User c;
c = a;           // copy ASSIGNMENT: c already exists
```

| | Copy constructor | Copy assignment |
|---|---|---|
| Signature | `T(const T& other)` | `T& operator=(const T& other)` |
| Called when | a new object is made from an existing one (initialization, pass or return by value) | an existing object is overwritten |
| Old state | none | must release old resources and survive `a = a` |
| Returns | nothing | `*this`, so `a = b = c` chains |

The parameter must be a reference: taking it by value would require a copy to make the copy, recursing forever (the compiler rejects `T(T)`).

A class that owns heap memory shows why the defaults are not enough. This one implements all five special members:

```cpp
#include <cstring>
#include <utility>

class String {
public:
    String(const char* s = "") : size_(std::strlen(s)), data_(new char[size_ + 1]) {
        std::memcpy(data_, s, size_ + 1);              // includes the '\0'
    }
    ~String() { delete[] data_; }                     // 1. destructor

    String(const String& other)                       // 2. copy constructor: DEEP copy
        : size_(other.size_), data_(new char[other.size_ + 1]) {
        std::memcpy(data_, other.data_, size_ + 1);
    }

    String& operator=(const String& other) {          // 3. copy assignment
        if (this != &other) {                         // self-assignment guard
            char* fresh = new char[other.size_ + 1];  // allocate first: if new throws, *this is untouched
            std::memcpy(fresh, other.data_, other.size_ + 1);
            delete[] data_;
            data_ = fresh;
            size_ = other.size_;
        }
        return *this;
    }

    String(String&& other) noexcept                   // 4. move constructor: steal the buffer
        : size_(other.size_), data_(other.data_) {
        other.size_ = 0;
        other.data_ = nullptr;
    }

    String& operator=(String&& other) noexcept {      // 5. move assignment
        if (this != &other) {
            delete[] data_;
            data_ = std::exchange(other.data_, nullptr);
            size_ = std::exchange(other.size_, 0);
        }
        return *this;
    }

    const char* c_str() const { return data_ ? data_ : ""; }
    std::size_t size() const { return size_; }

private:
    std::size_t size_;     // declared before data_, so it is initialized first
    char* data_;
};
```

What goes wrong with only the first constructor and the destructor (a **shallow copy**):

```cpp
{
    String a("hi");
    String b = a;   // compiler copy: b.data_ == a.data_, one buffer, two owners
}                   // ~b deletes the buffer, then ~a deletes it again: double free
```

Shallow copies also make edits through one object visible in the other, and the default assignment leaks the old buffer. A **deep copy** allocates a new buffer and copies the contents.

Going deeper: the **copy-and-swap** idiom replaces both assignment operators with one, `String& operator=(String other) noexcept`, that swaps members with its by-value parameter. The copy or move happens while building the argument, so self-assignment is safe and a failed allocation leaves `*this` untouched (the strong guarantee).

## 5. Rule of 3, 5 and 0

- **Rule of 3** (C++98): a class that needs a custom destructor, copy constructor or copy assignment almost certainly needs all three, because it manages a resource.
- **Rule of 5** (C++11): add the move constructor and move assignment. Declaring a destructor or a copy operation suppresses the implicit moves, so the class silently copies where it could move.
- **Rule of 0**: design classes to need none of the five. Hold resources in RAII members and let the compiler generate everything.

```cpp
struct Renderer { virtual ~Renderer() = default; };

class Document {                            // Rule of 0: no destructor, no copy or move code
    std::string title_;
    std::vector<std::string> lines_;
    std::unique_ptr<Renderer> renderer_;    // makes Document move-only automatically
};
```

| If you declare... | Implicit copy operations | Implicit move operations |
|---|---|---|
| none of the five | generated | generated |
| a destructor | generated (deprecated) | not declared: moves fall back to copies |
| a copy constructor or copy assignment | the other one is generated (deprecated) | not declared |
| a move constructor or move assignment | deleted | the other one is not declared |

Declaring any constructor removes the implicit default constructor. `= default` requests the generated version; `= delete` forbids an operation, as in `NonCopyable(const NonCopyable&) = delete;`.

## 6. this and static members

```cpp
class Counter {
public:
    Counter() { ++alive_; }
    Counter(const Counter& other) : value_(other.value_) { ++alive_; }
    ~Counter() { --alive_; }

    Counter& add(int n) { value_ += n; return *this; }   // returning *this enables chaining
    static int alive() { return alive_; }                // no this: cannot touch value_
private:
    int value_ = 0;
    static inline int alive_ = 0;   // C++17; earlier: declare here, define "int Counter::alive_ = 0;" in one .cpp
};

Counter c;
c.add(1).add(2);                    // value_ == 3
std::cout << Counter::alive();      // 1
```

`this` is a pointer to the current object (`const T*` inside const member functions). It is used for chaining, self-assignment checks, `this->name = name;` when a parameter shadows a member, and passing the object to other functions. Static member functions cannot be `virtual` or `const`: both need an object.

## 7. Operator overloading and friends

```cpp
#include <iostream>
#include <vector>

class Money {
public:
    explicit Money(long cents = 0) : cents_(cents) {}
    Money& operator+=(const Money& rhs) { cents_ += rhs.cents_; return *this; }   // member: changes *this
    bool operator==(const Money& rhs) const { return cents_ == rhs.cents_; }
    bool operator!=(const Money& rhs) const { return !(*this == rhs); }         // C++20 derives this from ==
    friend std::ostream& operator<<(std::ostream& os, const Money& m) {         // non-member friend
        return os << m.cents_ << " cents";
    }
private:
    long cents_;
};

Money operator+(Money lhs, const Money& rhs) { lhs += rhs; return lhs; }   // non-member, built on +=

class IntArray {
public:
    explicit IntArray(std::size_t n) : data_(n) {}
    int& operator[](std::size_t i) { return data_[i]; }               // writable: arr[2] = 5
    const int& operator[](std::size_t i) const { return data_[i]; }   // read-only on const objects
private:
    std::vector<int> data_;
};

Money total = Money(150) + Money(250);
std::cout << total << '\n';    // 400 cents
```

| Operator | Usually | Why |
|---|---|---|
| `=`, `[]`, `()`, `->`, conversion operators | member | required by the language |
| `+=`, `-=`, `++`, `--` | member | they modify `*this` |
| `+`, `-`, `==`, `<` | non-member (often built on the compound member) | symmetric: conversions apply to both operands |
| `<<`, `>>` with streams | non-member, often `friend` | the left operand is a `std::ostream` you cannot add members to |

- Prefix `T& operator++()` returns the updated object; postfix `T operator++(int)` takes a dummy `int` and returns the old value by copy, which is why `++it` is preferred for iterators. Avoid overloading `&&` and `||`: the overloads lose short-circuit evaluation.
- A `friend` function or class may access private members. Friendship is granted by the class, never taken, and is not inherited, transitive or mutual. Typical uses: stream operators, symmetric operators, tightly coupled helper classes.

## 8. Inheritance: access modes and constructor order

```cpp
class Shape {
public:
    explicit Shape(std::string name) : name_(std::move(name)) {}
    virtual ~Shape() = default;                         // polymorphic base: virtual destructor
    virtual double area() const = 0;                    // pure virtual: Shape is abstract
    const std::string& name() const { return name_; }
private:
    std::string name_;
};

class Circle : public Shape {
public:
    explicit Circle(double r) : Shape("circle"), r_(r) {}   // the base constructor runs first
    double area() const override { return 3.14159 * r_ * r_; }
private:
    double r_;
};
```

| Base member | `public` inheritance | `protected` inheritance | `private` inheritance |
|---|---|---|---|
| public | public | protected | private |
| protected | protected | protected | private |
| private | not accessible | not accessible | not accessible |

- `class D : B` is private inheritance by default, `struct D : B` public: always write the keyword. Only public inheritance models "is-a" (outside code can convert `Circle*` to `Shape*`); private inheritance means "implemented in terms of", and composition is usually clearer.
- Order: virtual bases, then direct bases left to right as listed, then members in declaration order, then the body. A base without a default constructor must be called in the initializer list.
- Constructors, the destructor, copy assignment and friendship are not inherited (`using Base::Base;` inherits constructors since C++11).

## 9. Virtual functions, vtables and dynamic dispatch

```cpp
#include <iostream>
#include <memory>
#include <vector>

struct Animal {
    virtual ~Animal() = default;
    virtual void speak() const { std::cout << "...\n"; }
    void kind() const { std::cout << "animal\n"; }       // non-virtual: bound at compile time
};

struct Dog : Animal {
    void speak() const override { std::cout << "Woof\n"; }
    void kind() const { std::cout << "dog\n"; }          // hides Animal::kind, no dispatch
};

int main() {
    Dog d;
    Animal& ref = d;
    Animal* ptr = &d;
    ref.speak();      // Woof:   virtual, uses the dynamic type
    ptr->speak();     // Woof
    ptr->kind();      // animal: non-virtual, uses the static type Animal*
    d.kind();         // dog

    std::vector<std::unique_ptr<Animal>> zoo;
    zoo.push_back(std::make_unique<Dog>());
    for (const auto& a : zoo) a->speak();   // Woof
}
```

How dynamic dispatch works (the answer interviewers want):
1. For each class with virtual functions, the compiler builds one **vtable**: a static array of function pointers, one slot per virtual function, each pointing to the most-derived implementation for that class.
2. Each object of such a class holds a hidden **vptr** (typically its first 8 bytes), which the constructor sets to its class's vtable.
3. `ptr->speak()` compiles to: load the object's vptr, load the `speak` slot, call that address with `ptr` as `this`. The object's real type decides, not the pointer's type.
4. Cost: one pointer per object, one table per class, and an indirect call that usually cannot be inlined.

```text
Dog object          Dog vtable            Animal object       Animal vtable
+--------+          +------------+        +--------+          +---------------+
| vptr --+--------> | ~Dog       |        | vptr --+--------> | ~Animal       |
| fields |          | Dog::speak |        | fields |          | Animal::speak |
+--------+          +------------+        +--------+          +---------------+
```

- vtables are an implementation technique rather than part of the standard, but GCC, Clang and MSVC all use them.
- While a base constructor or destructor runs, the vptr points at the base's vtable (the derived part does not exist yet, or is already gone), so virtual calls there run the base version. Calling a pure virtual function that way is undefined behavior.

| | Static (early) binding | Dynamic (late) binding |
|---|---|---|
| Decided | at compile time | at run time |
| Applies to | non-virtual calls, overloads, templates, calls on objects by value | virtual calls through a pointer or reference |
| Cost | can be inlined | indirect call through the vtable |

## 10. Abstract classes, virtual destructors, override and final

```cpp
struct PaymentGateway {                     // C++ has no interface keyword: pure virtuals + virtual destructor
    virtual ~PaymentGateway() = default;
    virtual bool charge(long cents) = 0;
};
// PaymentGateway g;   // error: abstract, like Shape in section 8
```

A derived class stays abstract until it overrides every pure virtual function. A pure virtual function may still have a body (callable as `Base::f()`), and a pure virtual destructor must have one. In your web stack: Ruby has no abstract classes (convention: a base method that raises `NotImplementedError`, or plain duck typing), while TypeScript has `abstract class` and `interface`.

**Virtual destructors:**

```cpp
struct Base { ~Base() { std::cout << "~Base\n"; } };     // NOT virtual
struct Derived : Base {
    std::vector<int> data = std::vector<int>(1000);
    ~Derived() { std::cout << "~Derived\n"; }
};

Base* p = new Derived;
delete p;   // undefined behavior: in practice only ~Base runs, so data leaks
```

With `virtual ~Base()`, `delete p` dispatches through the vtable to `~Derived`, which then runs `~Base` automatically. Rule: a class meant for polymorphic use gets a public virtual destructor (or a protected non-virtual one so nobody can delete through the base). Going deeper: `std::shared_ptr<Base> sp = std::make_shared<Derived>();` destroys correctly even without a virtual destructor, because the control block remembers the real type; `std::unique_ptr<Base>` does not. Do not rely on it.

**override and final:**

```cpp
struct Widget {
    virtual void draw(int scale) const;
    virtual void reset();
};
struct Button : Widget {
    void draw(int scale) override;   // error: missing const, so it overrides nothing
    void reset() final;              // overrides; classes derived from Button cannot override it again
};
class IconButton final : public Button {};   // nothing may derive from IconButton
```

Without `override`, the mismatched `draw` compiles as a new function that hides the base one, and calls through a `Widget&` silently run the base version. `final` also lets the compiler devirtualize calls.

## 11. Object slicing

```cpp
void byValue(Animal a) { a.speak(); }      // copies only the Animal part
void byRef(const Animal& a) { a.speak(); }

Dog d;
byValue(d);              // ...   (sliced: a is a real Animal)
byRef(d);                // Woof
std::vector<Animal> pets;
pets.push_back(d);       // sliced too: store std::unique_ptr<Animal> instead
```

An `Animal` object only has room for `Animal`'s members, and `Animal`'s copy constructor copies the base part and gives the copy `Animal`'s vptr. Avoid slicing by passing and storing polymorphic objects through references or (smart) pointers, catching exceptions by reference, and deleting the base's copy operations so slicing becomes a compile error.

## 12. Multiple inheritance and the diamond

```cpp
#include <iostream>

struct Device {
    explicit Device(int id) : id(id) { std::cout << "Device\n"; }
    int id;
};
struct Printer : virtual Device { Printer() : Device(1) {} };
struct Scanner : virtual Device { Scanner() : Device(2) {} };
struct Copier : Printer, Scanner {
    Copier() : Device(3) {}        // the most-derived class constructs the shared virtual base
};

int main() {
    Copier c;                      // prints "Device" once
    std::cout << c.id << '\n';     // 3: one Device subobject, no ambiguity
}
```

- Without `virtual`, a `Copier` contains two `Device` subobjects: the state is duplicated and `c.id` is ambiguous (you would write `c.Printer::id`). That is the **diamond problem**.
- With virtual inheritance there is one shared subobject reached through an extra indirection. Virtual bases are constructed first, by the most-derived class; the `Device(1)` and `Device(2)` initializers are ignored when building a `Copier`.
- Inheriting several interfaces (pure abstract classes) is common and safe; inheriting state from several bases is where diamonds hurt. Prefer composition.
- In your web stack: Ruby avoids the diamond with single inheritance plus modules arranged in one linear ancestor chain (see [Ruby modules and mixins](../ruby/03-oop-modules-mixins.md)); TypeScript allows one `extends` and many `implements`.

## 13. Name hiding

```cpp
struct Base {
    void f(int) { std::cout << "Base::f(int)\n"; }
    void f(double) { std::cout << "Base::f(double)\n"; }
};
struct Derived : Base {
    void f(const char*) { std::cout << "Derived::f(const char*)\n"; }   // hides BOTH Base::f overloads
    // using Base::f;   // uncomment to bring the base overloads back
};

Derived d;
d.f("hi");   // Derived::f(const char*)
d.f(1);      // error: lookup stops at Derived::f, and int does not convert to const char*
```

Name lookup finds the name in the nearest scope first and only then runs overload resolution, so overloads never mix across scopes. Overriding one virtual overload hides the others in the same way.

## 14. Templates

```cpp
template <typename T>
T maxOf(T a, T b) { return a > b ? a : b; }

template <>                                      // full specialization for C strings
const char* maxOf(const char* a, const char* b) { return std::strcmp(a, b) > 0 ? a : b; }

template <typename T>
class Stack {
public:
    void push(const T& x) { items_.push_back(x); }
    void pop() { items_.pop_back(); }
    const T& top() const { return items_.back(); }
private:
    std::vector<T> items_;
};

maxOf(3, 7);             // T = int, deduced
maxOf<double>(3, 7.5);   // explicit T (maxOf(3, 7.5) fails: T cannot be both int and double)
Stack<std::string> s;
s.push("hi");
```

- The compiler generates a separate function or class for each set of template arguments you use (**instantiation**): no runtime cost, but bigger binaries and long error messages.
- Templates live in headers because every translation unit needs the full definition to instantiate it; defining template members in a `.cpp` causes "undefined reference" link errors.
- Class templates also allow partial specialization (`template <typename T> class Stack<T*>`) and non-type parameters (`template <typename T, std::size_t N>`).
- Templates are compile-time (static) polymorphism; virtual functions are run-time polymorphism. Going deeper: C++20 concepts (`template <std::integral T>`) state requirements on `T` and give readable errors.

## 15. RTTI and dynamic_cast

```cpp
#include <typeinfo>

void describe(const Animal& a) {
    if (const auto* dog = dynamic_cast<const Dog*>(&a))   // pointer form: nullptr if not a Dog
        dog->kind();                                       // safe to use Dog-only members
    // reference form: dynamic_cast<const Dog&>(a) throws std::bad_cast instead
    std::cout << typeid(a).name() << '\n';                 // dynamic type; spelling is compiler-specific
}
```

| Cast | Checked | Use for |
|---|---|---|
| `static_cast` | compile time only | numeric conversions, upcasts, downcasts you know are safe |
| `dynamic_cast` | run time (needs a polymorphic base) | safe downcasts and cross-casts |
| `const_cast` | no | adding or removing `const` (writing to a truly const object is UB) |
| `reinterpret_cast` | no | low-level reinterpretation of bits |
| C-style `(T)x` | tries the above in turn | avoid: hides which cast happens |

RTTI (run-time type information) is stored next to the vtable, so `dynamic_cast` and `typeid` on dynamic types only work for polymorphic classes, and some projects disable it (`-fno-rtti`). Long `dynamic_cast` chains are a design smell: a virtual function on the base is usually the better answer.

## Common pitfalls
- A polymorphic base without a virtual destructor.
- A class owning raw memory with compiler-generated copies (shallow copy, double free): the Rule of 3/5 was broken.
- Slicing (polymorphic objects passed or stored by value, exceptions caught by value); expecting derived behavior from virtual calls in constructors or destructors.
- An "override" with a slightly different signature (missing `const`, `int` vs `long`) and no `override` keyword.
- An initializer list in a different order from the member declarations; copy assignment that breaks on `a = a` or deletes before the new allocation succeeds.
- A single-argument constructor without `explicit`, so `charge(500)` silently builds a `Money` from an `int`.
- An overload added in a derived class hiding the base overloads; template definitions placed in `.cpp` files.

## Interview questions

**Q1. What is the difference between a class and a struct in C++?**
Only the defaults: `class` members and base classes are private by default, `struct` ones are public. Both can have constructors, virtual functions and inheritance. By convention, `struct` is used for plain data and `class` for types that protect an invariant.

**Q2. Why do we need a virtual destructor? What happens without one?**
If a derived object is deleted through a base pointer and the base destructor is not virtual, the behavior is undefined; in practice only the base destructor runs, so the derived members (and their resources) leak. With a virtual destructor, `delete basePtr` dispatches to the derived destructor, which then calls the base one.
*Follow-up:* Does every class need one? No: only classes meant to be used polymorphically. A virtual destructor adds a vptr to otherwise plain types.

**Q3. How do virtual functions work under the hood?**
Each polymorphic class has a vtable, a static array of pointers to its virtual function implementations. Each object stores a hidden vptr to its class's vtable, set by the constructor. A virtual call through a pointer or reference loads the vptr, picks the slot for that function and calls it indirectly, so the object's dynamic type decides. Cost: a pointer per object, a table per class, and calls that are hard to inline.

**Q4. Can a constructor be virtual?**
No. Virtual dispatch needs a vptr, which the constructor itself sets up, and creating an object requires knowing its exact type. To copy polymorphically, use the "virtual constructor" idiom: a virtual `clone()` in the base, implemented in each derived class as `return std::make_unique<Square>(*this);`. Destructors, by contrast, can and often must be virtual.

**Q5. What happens if you call a virtual function from a constructor?**
It calls the version of the class whose constructor is running, not the derived override. During base construction the derived part does not exist yet, so the vptr still points to the base vtable. Calling a pure virtual function this way is undefined behavior (often a "pure virtual function called" crash). The same applies in destructors.

**Q6. Explain the Rule of 3, 5 and 0.**
Rule of 3: a class that needs a custom destructor, copy constructor or copy assignment usually needs all three because it owns a resource. Rule of 5: also define the move constructor and move assignment, since declaring the others suppresses the implicit moves. Rule of 0: preferably need none, by holding resources in RAII members (`std::string`, `std::vector`, `std::unique_ptr`) so the generated operations are correct.

**Q7. What is the difference between a shallow and a deep copy?**
A shallow copy copies member values, so two objects end up sharing the same heap buffer through copied pointers. Destroying both frees the buffer twice, and changes through one show in the other. A deep copy allocates new storage and copies the contents, so each object owns its own data. The compiler's default copy is shallow for raw pointers.
*Follow-up:* How do you avoid writing deep-copy code? Use `std::vector` or `std::string` members (Rule of 0).

**Q8. What is the difference between the copy constructor and copy assignment? Why does the copy constructor take a reference?**
The copy constructor initializes a brand-new object (`T b = a;`, pass or return by value); copy assignment replaces the contents of an existing object (`b = a;`) and must release old resources and handle self-assignment. The parameter must be a reference, because passing by value would itself need the copy constructor, recursing forever.

**Q9. What is object slicing and how do you avoid it?**
When a derived object is copied into a base object by value (parameter, assignment, `std::vector<Base>`), only the base part is copied and the copy behaves as a base, with no derived overrides. Avoid it by using references or smart pointers for polymorphic objects, catching exceptions by reference, and disabling copying in polymorphic bases.

**Q10. What is the diamond problem and how does virtual inheritance solve it?**
If `B` and `C` both inherit from `A` and `D` inherits from both, `D` contains two `A` subobjects: duplicated state and ambiguous member access. Declaring `B : virtual A` and `C : virtual A` makes `D` share a single `A`, which the most-derived class constructs first. Java and C# sidestep the problem with single class inheritance plus interfaces.

**Q11. What is an abstract class? How do you define an interface in C++?**
A class with at least one pure virtual function (`virtual void f() = 0;`); it cannot be instantiated and derived classes must override every pure virtual function to become concrete. An interface is an abstract class with only pure virtual functions and a virtual destructor, typically inherited publicly, possibly several at once.

**Q12. What do `override` and `final` do?**
`override` asks the compiler to verify the function really overrides a base virtual; any signature mismatch becomes a compile error instead of a silent new function. `final` on a virtual function forbids further overriding; on a class it forbids inheritance and lets the compiler devirtualize calls.

**Q13. Why is `operator<<` overloaded as a non-member? Doesn't `friend` break encapsulation?**
In `std::cout << obj` the left operand is the stream, and a member operator would need to be a member of `std::ostream`, which you cannot change. It is declared `friend` when it needs private data. Friendship is granted explicitly by the class and limited to that function, so it extends the class's interface rather than breaking it; a public getter can expose more.

**Q14. Templates vs virtual functions: when do you use each?**
Templates give compile-time polymorphism: the type is known at compile time, calls can be inlined, and each type gets its own generated code (fast, but bigger binaries and the type is fixed at build time). Virtual functions give run-time polymorphism: one compiled function works on objects chosen at run time, at the cost of an indirect call. Use templates for generic containers and algorithms, virtual functions for heterogeneous collections and plug-in behavior.

**Q15. When would you use `dynamic_cast`, and what does it cost?**
To downcast safely from a polymorphic base when you cannot avoid needing the derived type: the pointer form returns `nullptr` on failure and the reference form throws `std::bad_cast`. It walks RTTI at run time, so it is slower than `static_cast`. Frequent use signals that a virtual function belongs on the base class.
