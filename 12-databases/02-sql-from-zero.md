## Quick revision
- Sublanguages: **DDL** (CREATE, ALTER, DROP, TRUNCATE), **DML** (INSERT, UPDATE, DELETE, MERGE), **DQL** (SELECT), **DCL** (GRANT, REVOKE), **TCL** (BEGIN, COMMIT, ROLLBACK, SAVEPOINT).
- Logical order: `FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT (window functions) -> DISTINCT -> ORDER BY -> LIMIT/OFFSET`. That is why WHERE cannot use a SELECT alias but ORDER BY can.
- **WHERE** filters rows before grouping; **HAVING** filters groups after aggregation.
- `INNER JOIN` keeps matches only; `LEFT JOIN` keeps every left row (NULLs when no match); `FULL JOIN` keeps both sides; `CROSS JOIN` is every combination.
- A filter on the right table of a LEFT JOIN belongs in `ON`, not `WHERE`, or the join silently becomes inner.
- Anti-join ("rows with no match"): `NOT EXISTS` (safest) or `LEFT JOIN ... WHERE right.id IS NULL`. Avoid `NOT IN (subquery)` when the subquery can return NULL: it returns no rows at all.
- `COUNT(*)` counts rows, `COUNT(col)` counts non-NULL values, `COUNT(DISTINCT col)` counts distinct non-NULL values. Other aggregates ignore NULLs too.
- `ROW_NUMBER` 1,2,3,4 (always unique) / `RANK` 1,2,2,4 (gaps) / `DENSE_RANK` 1,2,2,3 (no gaps).
- Window functions compute per row without collapsing rows: `SUM(x) OVER (PARTITION BY a ORDER BY b)`.
- `UNION` removes duplicates (extra sort/hash work), `UNION ALL` keeps them and is faster.
- NULL logic is three-valued: `NULL = NULL` is NULL (unknown). Use `IS NULL`, `IS DISTINCT FROM`, `COALESCE`.
- Postgres extras: `ILIKE`, `RETURNING`, `ON CONFLICT` upsert, `DISTINCT ON`, `FILTER (WHERE ...)`, `generate_series`.
- `DELETE` removes chosen rows (WHERE, triggers fire); `TRUNCATE` empties the table fast (no WHERE); `DROP` removes the table itself.

## 1. The sample schema

Every example in this file and in [03](03-sql-practice-problems.md) uses this schema (03 has the full seed script). Revenue counts only `paid` and `shipped` orders.

```sql
CREATE TABLE departments (
  id   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE
);

CREATE TABLE employees (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name          text NOT NULL,
  email         text NOT NULL UNIQUE,
  department_id bigint REFERENCES departments(id) ON DELETE SET NULL,
  manager_id    bigint REFERENCES employees(id),          -- self-reference: org chart
  salary        numeric(10,2) NOT NULL CHECK (salary > 0),
  hired_on      date NOT NULL
);

CREATE TABLE categories (
  id        bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name      text NOT NULL,
  parent_id bigint REFERENCES categories(id)               -- self-reference: category tree
);

CREATE TABLE products (
  id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name        text NOT NULL,
  category_id bigint REFERENCES categories(id),
  price       numeric(10,2) NOT NULL CHECK (price >= 0),
  active      boolean NOT NULL DEFAULT true
);

CREATE TABLE customers (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  city       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  status      text NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  ordered_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id   bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products(id),
  quantity   integer NOT NULL CHECK (quantity > 0),
  unit_price numeric(10,2) NOT NULL                        -- price at purchase time
);

-- Postgres does not index foreign keys automatically
CREATE INDEX ON employees (department_id);
CREATE INDEX ON employees (manager_id);
CREATE INDEX ON products (category_id);
CREATE INDEX ON orders (customer_id, ordered_at);
CREATE INDEX ON order_items (order_id);
CREATE INDEX ON order_items (product_id);
```

`GENERATED BY DEFAULT AS IDENTITY` lets a seed script insert explicit ids; `GENERATED ALWAYS` is stricter (see [PostgreSQL](04-postgresql.md)).

## 2. The SQL sublanguages

| Group | Statements | Notes |
|---|---|---|
| DDL (definition) | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `COMMENT` | Transactional in Postgres (a failed migration rolls back fully); implicit commit in MySQL |
| DML (manipulation) | `INSERT`, `UPDATE`, `DELETE`, `MERGE` | Row changes |
| DQL (query) | `SELECT` | Often grouped into DML |
| DCL (control) | `GRANT`, `REVOKE` | Privileges on tables, schemas, roles |
| TCL (transaction control) | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | See [06](06-transactions-and-concurrency.md) |

```sql
ALTER TABLE customers ADD COLUMN phone text;
ALTER TABLE customers ALTER COLUMN city SET NOT NULL;      -- fails if any NULLs exist
ALTER TABLE customers RENAME COLUMN phone TO phone_number;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reporting;
```

## 3. SELECT basics

```sql
SELECT name, salary
FROM employees
WHERE department_id IN (1, 2)                 -- set membership
  AND salary BETWEEN 90000 AND 200000         -- inclusive on both ends
  AND email LIKE '%@example.com'              -- % any run of chars, _ exactly one char
  AND manager_id IS NOT NULL                  -- never "= NULL"
ORDER BY salary DESC, name ASC                -- tie-breaker makes order deterministic
LIMIT 5 OFFSET 0;

SELECT * FROM customers WHERE name ILIKE 'a%';   -- case-insensitive LIKE (Postgres only)
SELECT DISTINCT city FROM customers;             -- unique values
SELECT DISTINCT ON (customer_id) *               -- Postgres: first row per customer_id
FROM orders ORDER BY customer_id, ordered_at DESC;
```

- `BETWEEN` on timestamps is a trap: `ordered_at BETWEEN '2025-01-01' AND '2025-01-31'` misses everything after midnight on the 31st. Use a half-open range: `ordered_at >= '2025-01-01' AND ordered_at < '2025-02-01'`.
- Without `ORDER BY`, row order is undefined, even if it looks stable today.
- `LIMIT/OFFSET` pagination gets slower as the offset grows; see keyset pagination in [05](05-indexing-and-query-optimization.md).

## 4. Logical execution order

You write `SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT`, but the database logically evaluates:

| Step | Clause | Consequence |
|---|---|---|
| 1 | `FROM`, `JOIN` | Builds the row set |
| 2 | `WHERE` | Filters rows; cannot see aggregates or SELECT aliases |
| 3 | `GROUP BY` | Collapses rows into groups |
| 4 | `HAVING` | Filters groups; can use aggregates |
| 5 | `SELECT` | Computes expressions and window functions, assigns aliases |
| 6 | `DISTINCT` | Removes duplicate output rows |
| 7 | `ORDER BY` | Can use aliases and window results |
| 8 | `LIMIT` / `OFFSET` | Trims the final result |

The planner may physically reorder work (push filters down, pick join order), but the result must match this logical order. Window functions run at step 5, which is why you cannot put `ROW_NUMBER()` in WHERE: wrap it in a subquery or CTE.

## 5. Aggregates, GROUP BY, HAVING

```sql
SELECT d.name AS department,
       COUNT(e.id)            AS headcount,      -- COUNT(column) skips NULLs
       ROUND(AVG(e.salary), 2) AS avg_salary,
       MAX(e.salary)           AS top_salary
FROM departments d
LEFT JOIN employees e ON e.department_id = d.id
GROUP BY d.id, d.name
HAVING COUNT(e.id) >= 2            -- filter groups
ORDER BY headcount DESC;
```

- Every selected column must be grouped or aggregated. Postgres allows other columns of a table when you group by its primary key (functional dependency).
- `WHERE` vs `HAVING`: put row filters in WHERE (cheaper: fewer rows to group) and aggregate filters in HAVING. `HAVING salary > 100000` without an aggregate is legal but is just a slower WHERE.
- Useful aggregates: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `string_agg(name, ', ' ORDER BY name)`, `array_agg`, `bool_and`, `bool_or`, and the Postgres `FILTER` clause: `COUNT(*) FILTER (WHERE status = 'paid')`.
- `SUM` over zero rows returns NULL, not 0: wrap in `COALESCE(SUM(x), 0)`.

## 6. Joins

Take a tiny slice of the data: departments Engineering, Sales and Support; employees Bilal (Engineering), Zara (Sales) and Ali (no department).

```sql
SELECT e.name AS employee, d.name AS department
FROM employees e
JOIN departments d ON d.id = e.department_id;     -- swap JOIN for LEFT/RIGHT/FULL JOIN
```

| employee | department | in INNER | in LEFT | in RIGHT | in FULL |
|---|---|---|---|---|---|
| Bilal | Engineering | yes | yes | yes | yes |
| Zara | Sales | yes | yes | yes | yes |
| Ali | NULL | | yes | | yes |
| NULL | Support | | | yes | yes |

- **INNER**: only matching pairs. **LEFT**: all employees, NULLs where no department. **RIGHT**: all departments (rarely used; flip the tables and use LEFT). **FULL**: everything from both sides. **CROSS JOIN**: every combination, 3 x 3 = 9 rows (useful with `generate_series` to build calendars).
- A join multiplies rows: one order with three items becomes three rows. Aggregating order-level values after joining items double counts (see the AOV problem in [03](03-sql-practice-problems.md)).

**Self join** (a table joined to itself under two aliases):

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;     -- LEFT keeps the CEO (no manager)
```

**Semi-join and anti-join**: "rows that have / do not have a match".

```sql
-- Departments that have at least one employee (semi-join)
SELECT d.name FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.department_id = d.id);

-- Departments with no employees (anti-join), two equivalent forms
SELECT d.name FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.department_id = d.id);

SELECT d.name FROM departments d
LEFT JOIN employees e ON e.department_id = d.id
WHERE e.id IS NULL;                               -- test a NOT NULL column of the right table
```

Postgres plans both anti-join forms the same way in most cases. `NOT EXISTS` reads as the intent and is NULL-safe; `NOT IN` is not (section 11).

**The LEFT JOIN plus WHERE trap:**

```sql
-- Wrong: customers without paid orders vanish, because o.status is NULL for them
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';

-- Right: filter the right table inside ON
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid';
```

## 7. Subqueries

```sql
-- Scalar subquery: returns one value
SELECT name, salary, salary - (SELECT AVG(salary) FROM employees) AS diff_from_avg
FROM employees;

-- IN subquery: membership in a set
SELECT * FROM products
WHERE id IN (SELECT product_id FROM order_items);

-- EXISTS: stops at the first match, ignores what is selected
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'paid');

-- Correlated subquery: references the outer row, logically runs per outer row
SELECT e.name, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(x.salary) FROM employees x
                  WHERE x.department_id = e.department_id);
```

A scalar subquery that returns more than one row is a runtime error. Correlated subqueries are clear but can be slow on big tables; a join to a grouped subquery or a window function (`AVG(salary) OVER (PARTITION BY department_id)`) usually does the same work in one pass. Postgres also supports `LATERAL` joins, a correlated subquery in FROM that can return several rows (great for "top 3 per group").

## 8. CTEs and recursive CTEs

A CTE (`WITH`) names a subquery so complex queries read top to bottom:

```sql
WITH order_totals AS (
  SELECT o.id, o.customer_id, SUM(oi.quantity * oi.unit_price) AS total
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY o.id, o.customer_id
)
SELECT customer_id, COUNT(*) AS orders, ROUND(AVG(total), 2) AS avg_order_value
FROM order_totals
GROUP BY customer_id;
```

Since PostgreSQL 12, a CTE referenced once (with no side effects) can be inlined by the planner like a subquery; add `MATERIALIZED` to force computing it once, or `NOT MATERIALIZED` to force inlining. Before 12, CTEs were always an optimization fence.

A **recursive CTE** walks hierarchies: an anchor query, `UNION ALL`, and a recursive part that joins back to the CTE until it returns no rows.

```sql
WITH RECURSIVE org AS (
  SELECT id, name, manager_id, 0 AS depth, name::text AS path
  FROM employees WHERE manager_id IS NULL                    -- anchor: the top boss
  UNION ALL
  SELECT e.id, e.name, e.manager_id, org.depth + 1, org.path || ' > ' || e.name
  FROM employees e
  JOIN org ON e.manager_id = org.id                           -- recursive step
)
SELECT depth, path FROM org ORDER BY path;
```

Use it for org charts, category trees, comment threads and bill-of-materials. Guard against cycles in dirty data with a depth limit (`WHERE org.depth < 20`) or by tracking visited ids in an array.

## 9. Window functions

A window function computes a value across related rows while keeping every row, unlike GROUP BY which collapses them.

```sql
SELECT name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC, id) AS row_number,
       RANK()       OVER (ORDER BY salary DESC)     AS rank,
       DENSE_RANK() OVER (ORDER BY salary DESC)     AS dense_rank
FROM employees;
```

| name | salary | row_number | rank | dense_rank |
|---|---|---|---|---|
| Ayesha | 250000 | 1 | 1 | 1 |
| Hamza | 195000 | 2 | 2 | 2 |
| Bilal | 180000 | 3 | 3 | 3 |
| Zara | 150000 | 4 | 4 | 4 |
| Sana | 120000 | 5 | 5 | 5 |
| Fatima | 120000 | 6 | 5 | 5 |
| Omar | 110000 | 7 | 7 | 6 |
| Usman | 90000 | 8 | 8 | 7 |
| Hira | 90000 | 9 | 8 | 7 |
| Ali | 70000 | 10 | 10 | 8 |

- `PARTITION BY` restarts the calculation per group: `RANK() OVER (PARTITION BY department_id ORDER BY salary DESC)`. NULL keys form one partition of their own.
- Pick `ROW_NUMBER` for "exactly one row per group" (dedupe, latest row), `DENSE_RANK` for "Nth highest distinct value", `RANK` for competition-style ranking.
- `LAG(col, n)` / `LEAD(col, n)` read previous / next rows; `FIRST_VALUE`, `NTILE(4)` (quartiles), `PERCENT_RANK`, `CUME_DIST`.

```sql
SELECT id, customer_id, ordered_at,
       LAG(ordered_at) OVER w                          AS previous_order_at,
       ordered_at - LAG(ordered_at) OVER w             AS gap,
       COUNT(*) OVER w                                 AS running_order_count
FROM orders
WINDOW w AS (PARTITION BY customer_id ORDER BY ordered_at);
```

**Frames.** With `ORDER BY` inside `OVER`, aggregates use a default frame of `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which gives running totals but treats ties (peer rows with the same ORDER BY value) as one step. Be explicit when it matters:

```sql
SUM(revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)  -- running total
AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)          -- last 7 rows
AVG(revenue) OVER (ORDER BY day RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW) -- last 7 calendar days
```

`ROWS` counts physical rows; `RANGE` with an offset counts values (correct when days are missing). The classic bug: `LAST_VALUE(x) OVER (ORDER BY y)` returns the current row, because the default frame ends at the current row; add `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

## 10. CASE, COALESCE, NULLIF

```sql
SELECT name,
       CASE
         WHEN salary >= 180000 THEN 'senior'
         WHEN salary >= 100000 THEN 'mid'
         ELSE 'junior'                        -- without ELSE, unmatched rows get NULL
       END AS band,
       COALESCE(department_id::text, 'unassigned') AS dept    -- first non-NULL argument
FROM employees;

-- NULLIF(a, b) returns NULL when a = b: the classic division-by-zero guard
SELECT month, revenue / NULLIF(order_count, 0) AS avg_order_value FROM monthly_stats;

-- Conditional aggregation (pivot), portable and Postgres-specific forms
SELECT COUNT(CASE WHEN status = 'paid' THEN 1 END) AS paid_count,
       COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled_count
FROM orders;
```

`NULLIF(denominator, 0)` is the standard guard against division by zero: the result becomes NULL instead of an error. Integer division truncates in Postgres (`5 / 2 = 2`), so cast one side (`5::numeric / 2`) or multiply by `100.0`.

## 11. NULL and three-valued logic

NULL means "unknown", so comparisons with it are unknown, not false:

| Expression | Result |
|---|---|
| `NULL = NULL` | NULL |
| `NULL <> 1` | NULL |
| `NULL AND FALSE` | FALSE |
| `NULL AND TRUE` | NULL |
| `NULL OR TRUE` | TRUE |
| `NOT NULL` | NULL |
| `NULL IS NULL` | TRUE |
| `NULL IS DISTINCT FROM NULL` | FALSE |

WHERE keeps only rows where the condition is TRUE, so NULL rows silently drop out. `WHERE manager_id <> 5` excludes employees whose `manager_id` is NULL; write `WHERE manager_id IS DISTINCT FROM 5` if you want them.

**The NOT IN trap.** "Employees who manage nobody":

```sql
SELECT name FROM employees
WHERE id NOT IN (SELECT manager_id FROM employees);   -- returns ZERO rows
```

The CEO's `manager_id` is NULL, so for every employee the check becomes `id <> 1 AND id <> 2 AND ... AND id <> NULL`, which is never TRUE. Fix with `NOT EXISTS`, or filter the NULLs: `(SELECT manager_id FROM employees WHERE manager_id IS NOT NULL)`, which returns Sana, Hamza, Usman, Hira, Fatima and Ali.

Other NULL rules: aggregates skip NULLs (`AVG` of 10, NULL, 20 is 15); `GROUP BY` and `DISTINCT` put all NULLs in one group; in Postgres NULLs sort last in ascending order and first in descending order (override with `NULLS FIRST` / `NULLS LAST`); `||` with NULL gives NULL, while `concat()` and `concat_ws()` skip NULLs.

## 12. Set operations

```sql
SELECT email FROM customers
UNION                       -- removes duplicates (sorts or hashes the whole result)
SELECT email FROM employees;

SELECT customer_id FROM orders WHERE status = 'paid'
INTERSECT                   -- in both
SELECT customer_id FROM orders WHERE status = 'cancelled';

SELECT id FROM customers
EXCEPT                      -- in the first, not the second (MINUS in Oracle)
SELECT customer_id FROM orders;
```

Both sides need the same number of columns with compatible types; column names come from the first query; one `ORDER BY` at the end applies to the whole result. Prefer `UNION ALL` whenever duplicates are impossible or wanted: it skips the dedupe step. `INTERSECT ALL` and `EXCEPT ALL` keep duplicate counts.

## 13. Changing data

```sql
INSERT INTO customers (name, email, city)
VALUES ('Saad', 'saad@example.com', 'Karachi'),
       ('Amna', 'amna@example.com', 'Lahore')
RETURNING id, created_at;                         -- get generated values back, no second query

UPDATE products SET price = price * 1.10
WHERE category_id = 2
RETURNING id, name, price;

-- UPDATE with a join (Postgres: UPDATE ... FROM)
UPDATE order_items oi
SET unit_price = p.price
FROM products p
WHERE p.id = oi.product_id AND oi.order_id = 11;

-- DELETE with a join (Postgres: DELETE ... USING)
DELETE FROM orders o
USING customers c
WHERE c.id = o.customer_id AND c.email = 'test@example.com' AND o.status = 'pending';

-- Insert from a query
INSERT INTO products (name, category_id, price)
SELECT name || ' (refurbished)', category_id, price * 0.8 FROM products WHERE category_id = 1;
```

**Upsert** (insert, or update when a unique key already exists), Postgres 9.5+:

```sql
INSERT INTO customers (email, name, city)
VALUES ('ahmed@example.com', 'Ahmed Ali', 'Lahore')
ON CONFLICT (email)                                -- needs a unique index or constraint on email
DO UPDATE SET name = EXCLUDED.name, city = EXCLUDED.city   -- EXCLUDED = the row you tried to insert
RETURNING id;

INSERT INTO categories (id, name) VALUES (3, 'Books')
ON CONFLICT (id) DO NOTHING;                       -- skip silently
```

PostgreSQL 15 added the standard `MERGE` statement for more complex insert/update/delete-by-match logic. MySQL's equivalent of upsert is `INSERT ... ON DUPLICATE KEY UPDATE` ([MySQL essentials](07-mysql-essentials.md)). Always run a risky UPDATE or DELETE as a SELECT with the same WHERE first, or inside `BEGIN ... ROLLBACK`.

## 14. Views

```sql
CREATE VIEW customer_revenue AS
SELECT c.id, c.name, COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS revenue
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status IN ('paid', 'shipped')
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id, c.name;

SELECT * FROM customer_revenue WHERE revenue > 1000;   -- the view's query runs now
```

A view is a saved query (no stored data) used to simplify repeated joins or to expose a restricted set of columns. Materialized views store results; see [DBMS fundamentals](01-dbms-fundamentals.md).

## 15. Useful string and date functions (Postgres)

| Task | Expression | Result / note |
|---|---|---|
| Case | `lower(email)`, `upper(code)`, `initcap('ali raza')` | `Ali Raza` |
| Trim, length | `trim('  x ')`, `length('abc')` | `x`, `3` |
| Concatenate | `first || ' ' || last`, `concat_ws(', ', city, country)` | `concat_ws` skips NULLs |
| Substring | `substring('2025-06-15' FROM 1 FOR 7)`, `left(sku, 3)` | `2025-06` |
| Split | `split_part('a@b.com', '@', 2)` | `b.com` |
| Replace | `replace(phone, '-', '')`, `regexp_replace(s, '\s+', ' ', 'g')` | |
| Aggregate strings | `string_agg(name, ', ' ORDER BY name)` | one comma-separated string per group |
| Now | `now()` (timestamptz, start of transaction), `current_date` | |
| Truncate | `date_trunc('month', ordered_at)` | first instant of the month, great for grouping |
| Extract | `extract(year FROM hired_on)`, `extract(dow FROM d)` | |
| Arithmetic | `now() - interval '7 days'`, `age(hired_on)`, `d2 - d1` (dates give an integer of days) | |
| Format | `to_char(ordered_at, 'YYYY-MM')` | |
| Series | `generate_series('2025-06-01'::date, '2025-06-30', interval '1 day')` | calendar rows for gap filling |
| Time zones | `ordered_at AT TIME ZONE 'Asia/Karachi'` | timestamptz to local wall-clock time |

Keep functions off indexed columns in WHERE: `WHERE date_trunc('day', ordered_at) = '2025-06-15'` cannot use a plain index on `ordered_at`; the half-open range `ordered_at >= '2025-06-15' AND ordered_at < '2025-06-16'` can ([05](05-indexing-and-query-optimization.md)).

## 16. DELETE vs TRUNCATE vs DROP

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| Removes | Selected rows (WHERE) | All rows | The table: data, structure, indexes, privileges |
| Category | DML | DDL | DDL |
| Speed | Row by row, slow on big tables | Very fast (deallocates storage) | Fast |
| Triggers | ON DELETE row triggers fire | ON DELETE triggers do not fire (TRUNCATE triggers do) | None |
| Rollback | Yes | Yes in Postgres (transactional); implicit commit in MySQL | Yes in Postgres; not in MySQL |
| Identity/sequence | Not reset | `TRUNCATE ... RESTART IDENTITY` resets | Gone |
| Foreign keys | Checked per row, cascades apply | Fails if referenced unless `CASCADE` (truncates referencing tables too) | Fails if referenced unless `CASCADE` (drops the FK constraints) |
| Space | Leaves dead rows for VACUUM | Reclaimed immediately | Reclaimed |

## Common pitfalls
- `= NULL` instead of `IS NULL`: always unknown, so zero rows.
- `NOT IN` with a subquery that can produce NULL: zero rows. Use `NOT EXISTS`.
- Filtering the right table of a LEFT JOIN in WHERE: you get an inner join.
- Joining two one-to-many tables at once (orders to items and to payments) multiplies rows, so `SUM` double counts. Aggregate each child in its own subquery first.
- `BETWEEN` with timestamps and an inclusive end date. Use half-open ranges.
- Integer division: `SUM(paid) / COUNT(*)` gives 0 for ratios below 1. Multiply by `100.0` or cast to numeric.
- Missing `ORDER BY` with `LIMIT`: you get arbitrary rows.
- `SUM` or `AVG` over no rows is NULL; wrap with `COALESCE` when the UI expects 0.
- Ties in "top N": `LIMIT 1` hides the second person with the same max salary. Decide with the interviewer whether ties count, then pick `RANK`/`DENSE_RANK` or `ROW_NUMBER`.
- Running an UPDATE or DELETE without first running the same WHERE as a SELECT.

- Show that you use SQL directly, not only through ORMs: reading the SQL that ActiveRecord logs, or a report, data fix or backfill you wrote by hand on the Devntech client projects (both PostgreSQL). Use your real examples.

- When given a query problem, say the logical order out loud ("first I join, then filter rows, then group"), name your NULL and tie assumptions, and check edge cases at the end.

> **Fill in:** a query you wrote by hand on CrystalCommerce or Colochousing (a report, a data fix, a migration backfill), what it did and why the ORM version was not enough.

## Interview questions

**Q1. What is the difference between INNER JOIN and LEFT JOIN?**
INNER JOIN returns only rows with a match on both sides. LEFT JOIN returns every row from the left table and fills the right side's columns with NULL when there is no match. Use LEFT JOIN when the left rows must appear regardless, like "all customers with their order count, including zero".
*Follow-up:* How do you find customers with no orders? LEFT JOIN orders and keep `WHERE o.id IS NULL`, or use NOT EXISTS.

**Q2. What is the difference between WHERE and HAVING?**
WHERE filters individual rows before grouping and cannot use aggregates. HAVING filters groups after GROUP BY and can use aggregates like `COUNT(*) > 5`. Put everything you can in WHERE, because it shrinks the data before the expensive grouping step.
*Follow-up:* Can you use HAVING without GROUP BY? Yes, the whole result is treated as one group.

**Q3. Why can't you use a column alias from SELECT in WHERE?**
Because WHERE is evaluated before SELECT in the logical order (FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT). ORDER BY runs after SELECT, so it can use aliases. Repeat the expression in WHERE or wrap the query in a subquery/CTE.

**Q4. What is the difference between UNION and UNION ALL?**
UNION combines results and removes duplicates, which costs a sort or hash over the whole result. UNION ALL keeps every row and is faster. Use UNION ALL unless you actually need deduplication.

**Q5. Explain ROW_NUMBER, RANK and DENSE_RANK.**
All number rows in window order. ROW_NUMBER is always unique (1,2,3,4) even for ties. RANK gives ties the same number and leaves gaps (1,2,2,4). DENSE_RANK gives ties the same number without gaps (1,2,2,3). Use ROW_NUMBER to pick one row per group, DENSE_RANK for "Nth highest distinct value".
*Follow-up:* How do you make ROW_NUMBER deterministic? Add a unique tie-breaker to ORDER BY, like `id`.

**Q6. What is the difference between DELETE, TRUNCATE and DROP?**
DELETE removes selected rows, fires row triggers and is fully logged. TRUNCATE removes all rows at once, much faster, without row triggers, and can reset identities. DROP removes the table definition entirely. In Postgres all three are transactional; in MySQL, TRUNCATE and DROP cause an implicit commit.

**Q7. What does this return, and why: `SELECT * FROM employees WHERE id NOT IN (SELECT manager_id FROM employees)`?**
Zero rows if any `manager_id` is NULL (the CEO's is). `x NOT IN (..., NULL)` expands to `x <> ... AND x <> NULL`, which is never TRUE. Use NOT EXISTS or exclude NULLs in the subquery.

**Q8. What is the difference between COUNT(*), COUNT(column) and COUNT(DISTINCT column)?**
`COUNT(*)` counts rows. `COUNT(column)` counts rows where that column is not NULL. `COUNT(DISTINCT column)` counts unique non-NULL values. In the sample data: 10 employees, 9 with a department, 3 distinct departments.

**Q9. When do you use EXISTS instead of IN or a JOIN?**
EXISTS checks for the presence of a related row and stops at the first match, so it never duplicates outer rows the way a JOIN to a one-to-many table does. IN is fine for small literal lists and NULL-free subqueries. Modern planners often turn both into the same semi-join, so pick the clearest; for the negative case prefer NOT EXISTS.

**Q10. What is a CTE, and when do you use a recursive one?**
A CTE is a named subquery declared with WITH, used to make multi-step queries readable and reusable within one statement. A recursive CTE has an anchor part and a part that references the CTE itself, used for hierarchies: org charts, category trees, threaded comments. Guard against cycles with a depth limit.
*Follow-up:* Are CTEs slower than subqueries? Not since Postgres 12 for single-use CTEs (they get inlined); before that they were always materialized.

**Q11. What is the difference between a window function and GROUP BY?**
GROUP BY collapses each group into one output row. A window function computes over a set of related rows but keeps every input row, so you can show each employee's salary next to their department average or rank. Window functions run after WHERE/GROUP BY/HAVING, so filter on them from an outer query.

**Q12. How do you write an upsert in Postgres?**
`INSERT ... ON CONFLICT (unique_columns) DO UPDATE SET col = EXCLUDED.col`, or `DO NOTHING` to skip. The conflict target must match a unique index or constraint. It is atomic, unlike "SELECT then INSERT", which races under concurrency.
*Follow-up:* What does RETURNING give you with DO NOTHING? Nothing for the skipped rows, so select the existing row separately if you need its id.

**Q13. What is a self join? Give an example.**
Joining a table to itself with two aliases, used when rows reference other rows of the same table. Example: `employees e JOIN employees m ON m.id = e.manager_id` to show each employee with their manager, or to find employees who earn more than their manager.

**Q14. Why does this LEFT JOIN behave like an INNER JOIN: `LEFT JOIN orders o ON o.customer_id = c.id WHERE o.status = 'paid'`?**
For customers without orders, `o.status` is NULL, and `NULL = 'paid'` is unknown, so WHERE drops them. Move the condition into the ON clause to keep all customers.

**Q15. What are COALESCE and NULLIF used for?**
`COALESCE(a, b, c)` returns the first non-NULL argument, used for defaults (`COALESCE(SUM(x), 0)`). `NULLIF(a, b)` returns NULL when `a = b`, used to avoid division by zero: `revenue / NULLIF(orders, 0)`.

**Q16. What is the difference between DISTINCT and GROUP BY?**
`SELECT DISTINCT a, b` and `SELECT a, b ... GROUP BY a, b` return the same rows and usually get the same plan. Use GROUP BY when you also need aggregates per group; use DISTINCT to deduplicate output. Postgres's `DISTINCT ON (col)` keeps the first row per value according to ORDER BY.

**Q17. Why is OFFSET pagination slow on page 5000?**
The database must produce and throw away all the skipped rows, so cost grows with the offset, and inserts between requests shift pages (duplicates or skipped items). Keyset pagination (`WHERE (created_at, id) < (last_seen_created_at, last_seen_id) ORDER BY created_at DESC, id DESC LIMIT 20`) uses an index and stays fast. See [05](05-indexing-and-query-optimization.md).

**Q18. How would you safely run a bulk UPDATE in production?**
Run the same WHERE as a SELECT (or `SELECT count(*)`) first, then run the UPDATE inside a transaction and check the affected row count before COMMIT. For millions of rows, update in batches to avoid long locks and bloat, and use `RETURNING` or a backup table if you might need to revert.
