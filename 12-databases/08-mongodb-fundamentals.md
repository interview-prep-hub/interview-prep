> **On your resume:** RemoteDev internship: you built and integrated backend APIs with Next.js (TypeScript) and MongoDB. MongoDB is also in your skills list.

## Quick revision
- MongoDB stores **documents** (BSON: binary, typed JSON-like objects) in **collections** inside databases. No fixed schema unless you add `$jsonSchema` validation.
- Every document has a unique, immutable, automatically indexed `_id`, by default an **ObjectId**: 12 bytes = 4-byte timestamp + 5-byte random value + 3-byte counter (roughly time-ordered).
- Documents max out at **16 MB**. Single-document writes are **atomic**, including nested arrays: design so one business change touches one document.
- CRUD: `insertOne/insertMany`, `find(filter, projection)`, `updateOne/updateMany` with operators (`$set`, `$inc`, `$push`, `$addToSet`, `$pull`, `$unset`), `upsert: true`, `replaceOne`, `deleteOne/deleteMany`, `bulkWrite`.
- Query operators: `$eq $ne $gt $gte $lt $lte $in $nin $and $or $not $exists $type $regex $elemMatch $all $size`; dot notation for nested fields and arrays (`"items.sku"`).
- Arrays: `{ tags: "x" }` matches any element. Use **`$elemMatch`** when several conditions must hold for the same element.
- Indexes: single, compound (**ESR**: Equality, Sort, Range), multikey (arrays), text, **TTL** (auto-delete), unique, partial, hashed, wildcard. Check with `explain("executionStats")`: IXSCAN good, COLLSCAN bad, keys/docs examined close to returned.
- Write concern `w: "majority"` (the default in modern versions) survives failover; read concern `majority` reads only durable data; read preference picks primary or secondaries (stale reads).
- **Replica set**: one primary, secondaries replay the oplog; automatic election (about 10 s timeout) when the primary disappears.
- **Sharding**: partition a collection across shards by a shard key: high cardinality, even writes, present in most queries; avoid monotonically increasing ranged keys.
- Multi-document **transactions** exist (4.0 replica sets, 4.2 sharded clusters) but cost more; schema design should make them rare.
- Reuse one `MongoClient` per process (it owns a connection pool); cache it on `globalThis` in serverless and Next.js.

## 1. The document model and BSON

```js
// One document in db.orders
{
  _id: ObjectId("6650f1c2a1b2c3d4e5f60718"),
  storeId: ObjectId("664f0a9b8c7d6e5f4a3b2c1d"),
  customer: { name: "Ahmed", email: "ahmed@example.com", city: "Lahore" },   // embedded document
  items: [                                                                      // array of embedded documents
    { sku: "LAP-1", name: "Laptop", qty: 1, priceCents: 120000 },
    { sku: "MOU-1", name: "Mouse", qty: 2, priceCents: 2500 }
  ],
  status: "paid",
  tags: ["gift"],
  totalCents: 125000,
  createdAt: ISODate("2025-06-10T15:00:00Z")
}
```

| Relational | MongoDB |
|---|---|
| Database | Database |
| Table | Collection |
| Row | Document |
| Column | Field |
| Primary key | `_id` |
| Join | Embedding, or `$lookup` in aggregation |
| Foreign key | A stored reference (an ObjectId), **not enforced** |
| Multi-row transaction | Single-document atomicity; multi-document transactions when needed |

**BSON** is the binary encoding: length-prefixed (fast to skip fields) and typed beyond JSON: `ObjectId`, `Date`, `Int32`, `Int64`, `Double`, `Decimal128` (exact decimals, good for money), `Binary`, `Boolean`, `Null`, arrays and embedded documents. Limits: 16 MB per document, 100 levels of nesting.

**ObjectId** is generated by the driver, not the server: a 4-byte creation timestamp, a 5-byte random value and a 3-byte counter. It sorts roughly by creation time and `ObjectId(...).getTimestamp()` returns that time, but do not use it as a precise clock.

**Flexible schema** means the database does not force one shape, not that you should have none. Enforce the essentials with validation:

```js
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "role"],
      properties: {
        email: { bsonType: "string", pattern: "^.+@.+$" },
        role: { enum: ["student", "instructor", "admin"] }
      }
    }
  }
});
```

## 2. When MongoDB fits, and when SQL is better

| MongoDB fits | Prefer a relational database |
|---|---|
| Data read and written as a self-contained unit: a product with variants and specs, a course with modules, a CMS page | Many-to-many relationships queried from every side with ad hoc joins |
| Fields vary per item or evolve quickly | Strong cross-entity invariants: ledgers, inventory across warehouses, bookings |
| JSON end to end in a JavaScript/TypeScript stack | Heavy reporting and analytics with flexible SQL |
| Very high write volume with horizontal scaling (sharding) | Transactions spanning many entities are the norm, not the exception |
| Event logs, activity feeds, catalogs, user-generated content | Data whose integrity must be enforced by the database (foreign keys, CHECK) |

Both overlap a lot now: Postgres has JSONB, MongoDB has transactions and `$lookup`. The decision is about access patterns: in MongoDB you design the schema around the queries; in SQL you normalize and let queries join.

## 3. CRUD in mongosh

```js
use shop                                        // switch database (created lazily on first write)

db.products.insertOne({ sku: "LAP-1", name: "Laptop", priceCents: 120000, tags: ["electronics"], stock: 5 });
db.products.insertMany([
  { sku: "MOU-1", name: "Mouse", priceCents: 2500, tags: ["accessories"], stock: 40 },
  { sku: "KEY-1", name: "Keyboard", priceCents: 4500, tags: ["accessories"], stock: 0 }
], { ordered: false });                         // keep going if one document fails (e.g. duplicate key)

db.products.find({ priceCents: { $lt: 5000 } }, { name: 1, priceCents: 1, _id: 0 });  // filter + projection
db.products.findOne({ sku: "LAP-1" });
db.products.countDocuments({ stock: 0 });
```

Projection uses `1` to include and `0` to exclude; you cannot mix them in one projection, except for `_id: 0`.

**Update operators** change parts of a document in place:

```js
db.products.updateOne({ sku: "LAP-1" }, { $set: { priceCents: 115000 }, $inc: { stock: -1 } });
db.products.updateOne({ sku: "LAP-1" }, { $push: { tags: "sale" } });      // appends, even if present
db.products.updateOne({ sku: "LAP-1" }, { $addToSet: { tags: "sale" } });  // appends only if absent
db.products.updateOne({ sku: "LAP-1" }, { $pull: { tags: "sale" } });      // removes matching elements
db.products.updateOne({ sku: "LAP-1" }, { $unset: { legacyField: "" } });  // removes a field
db.products.updateMany({ stock: 0 }, { $set: { status: "out_of_stock" } });

// Keep only the 10 newest reviews embedded (a bounded array)
db.products.updateOne(
  { sku: "LAP-1" },
  { $push: { recentReviews: {
      $each: [{ rating: 5, text: "Great", createdAt: new Date() }],
      $sort: { createdAt: -1 },
      $slice: 10
  } } }
);
```

`updateOne(filter, { name: "x" })` without operators is rejected by modern drivers and mongosh ("update document requires atomic operators"); to swap the whole document deliberately, use `replaceOne(filter, newDoc)`. Mongoose wraps plain objects in `$set` for you, which hides the difference.

**Upsert, find-and-modify, delete, bulk:**

```js
// Insert if missing, update if present; equality fields from the filter are copied into a new document
db.marketPrices.updateOne(
  { productId: 101, source: "pricing_api", day: "2025-06-15" },
  { $set: { priceCents: 4599 }, $setOnInsert: { createdAt: new Date() } },
  { upsert: true }
);

// Atomic counter (for example invoice numbers): returns the updated document
db.counters.findOneAndUpdate({ _id: "invoice" }, { $inc: { seq: 1 } }, { upsert: true, returnNewDocument: true });

db.products.deleteOne({ sku: "KEY-1" });
db.sessions.deleteMany({ expiresAt: { $lt: new Date() } });

db.products.bulkWrite([
  { updateOne: { filter: { sku: "LAP-1" }, update: { $inc: { stock: -1 } } } },
  { insertOne: { document: { sku: "CAT-1", name: "Catan", priceCents: 5000 } } },
  { deleteOne: { filter: { sku: "OLD-1" } } }
], { ordered: false });
```

Two concurrent upserts with the same filter can both insert unless a **unique index** covers the filter fields; with the index, one fails with a duplicate-key error you can retry.

## 4. Query operators and dot notation

```js
db.orders.find({ status: { $in: ["paid", "shipped"] }, totalCents: { $gte: 10000, $lt: 50000 } });
db.orders.find({ $or: [{ status: "pending" }, { "customer.city": "Lahore" }] });  // dot notation into a subdocument
db.orders.find({ couponCode: { $exists: true } });
db.orders.find({ status: { $ne: "cancelled" } });            // also matches documents with no status field
db.orders.find({ "customer.email": /^ahmed/ });              // case-sensitive prefix regex: can use an index
db.orders.find({ "customer.email": { $regex: "example", $options: "i" } });  // unanchored: scans

// Arrays
db.orders.find({ tags: "gift" });                           // any element equals "gift"
db.orders.find({ tags: { $all: ["gift", "express"] } });    // contains both
db.orders.find({ items: { $size: 1 } });                    // exactly one element
db.orders.find({ "items.sku": "LAP-1" });                   // any item with that sku
db.orders.find({ items: { $elemMatch: { sku: "MOU-1", qty: { $gte: 2 } } } });  // the SAME item matches both
```

The `$elemMatch` trap: `{ "items.sku": "MOU-1", "items.qty": { $gte: 2 } }` also matches an order with one Mouse (qty 1) and a different item with qty 3, because each condition may be satisfied by a different element.

Top-level conditions are implicitly ANDed; explicit `$and` is needed only when you repeat the same field or operator (two `$or` groups, for example).

**Updating array elements:**
```js
db.orders.updateOne({ _id: orderId, "items.sku": "MOU-1" }, { $inc: { "items.$.qty": 1 } });  // first match
db.orders.updateOne({ _id: orderId }, { $set: { "items.$[].shipped": true } });               // every element
db.orders.updateMany(
  {},
  { $set: { "items.$[big].insured": true } },
  { arrayFilters: [{ "big.priceCents": { $gte: 100000 } }] }                                    // filtered elements
);
```

## 5. Sort, limit, skip and pagination

```js
db.orders.find({ storeId }).sort({ createdAt: -1, _id: -1 }).limit(20);              // page 1
db.orders.find({ storeId }).sort({ createdAt: -1, _id: -1 }).skip(40).limit(20);     // page 3: walks 40 first

// Range-based (keyset) pagination: continue after the last (createdAt, _id) the client saw
db.orders.find({
  storeId,
  $or: [
    { createdAt: { $lt: lastCreatedAt } },
    { createdAt: lastCreatedAt, _id: { $lt: lastId } }
  ]
}).sort({ createdAt: -1, _id: -1 }).limit(20);
```

`skip` has the same problem as SQL `OFFSET`: cost grows with the page number and results shift under inserts. With an index on `{ storeId: 1, createdAt: -1, _id: -1 }`, both the filter and the sort come from the index; a sort without a supporting index happens in memory and can hit the server's memory limit.

## 6. Indexes and explain()

```js
db.orders.createIndex({ storeId: 1 });                                  // single field
db.orders.createIndex({ storeId: 1, status: 1, createdAt: -1 });        // compound
db.products.createIndex({ tags: 1 });                                   // multikey: one entry per array element
db.products.createIndex({ name: "text", description: "text" });         // text: at most one per collection
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });   // TTL: delete once expiresAt passes
db.users.createIndex({ email: 1 }, { unique: true });
db.orders.createIndex({ createdAt: -1 }, { partialFilterExpression: { status: "pending" } });
db.events.createIndex({ userId: "hashed" });                            // hashed: for hashed sharding
db.products.createIndex({ "attributes.$**": 1 });                       // wildcard: unpredictable attribute keys
db.orders.getIndexes();
```

**The ESR rule** for compound index order: **E**quality fields first, then **S**ort fields, then **R**ange fields. For

```js
db.orders.find({ storeId: id, status: "paid", totalCents: { $gte: 10000 } }).sort({ createdAt: -1 });
```

the index is `{ storeId: 1, status: 1, createdAt: -1, totalCents: 1 }`. Equality fields narrow the scan to one contiguous block; placing the sort field before the range field lets MongoDB read entries already sorted instead of sorting in memory.

Index notes:
- **Multikey**: indexing an array field creates one key per element. A compound index can include at most one array field per document.
- **TTL**: works on Date fields; a background task removes expired documents roughly every 60 seconds, so expiry is not instant. Good for sessions, OTP codes, temporary carts, logs.
- **Unique** indexes on optional fields treat a missing field as `null`, so only one document may lack it; combine with a partial filter if the field is optional.
- **Text** indexes support `{ $text: { $search: "laptop bag" } }` with `{ $meta: "textScore" }` for ranking; Atlas Search (Lucene-based) is the serious option for search features.

**explain():**
```js
db.orders.find({ storeId: id, status: "paid" }).sort({ createdAt: -1 }).explain("executionStats");
```
Look at the winning plan's stages: `COLLSCAN` (full collection scan) is a red flag; `IXSCAN` followed by `FETCH` is normal; a `SORT` stage means an in-memory sort; `PROJECTION_COVERED` with `totalDocsExamined: 0` is a covered query. Compare `nReturned`, `totalKeysExamined` and `totalDocsExamined`: the closer to 1:1:1, the better the index fits. Atlas's Performance Advisor suggests indexes from real traffic.

## 7. Read concern, write concern and read preference

| Setting | Options | Meaning |
|---|---|---|
| Write concern | `w: 1`, `w: "majority"`, `j: true`, `wtimeout` | When a write is acknowledged: by the primary, or by a majority of voting members (survives failover); `j` waits for the on-disk journal |
| Read concern | `local` (default), `majority`, `linearizable`, `snapshot` | Which data a read may return: possibly not yet durable, only majority-committed, strictly the latest (single document, slow), or a transaction snapshot |
| Read preference | `primary` (default), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest` | Which member serves reads; anything but primary can return stale data |

Since MongoDB 5.0 the default write concern is `majority` for most deployments. With `w: 1`, a write acknowledged by a primary that crashes before replicating can be rolled back after the election. Causally consistent sessions give read-your-own-writes even when reading from secondaries.

## 8. Replica sets and elections

- A replica set is a group of `mongod` processes with the same data: one **primary** (accepts writes) and **secondaries** that copy the primary's **oplog** (an ordered log of operations) and apply it asynchronously.
- Members send heartbeats; if the primary is unreachable for the election timeout (10 seconds by default), eligible secondaries call an **election** and the one that wins a majority of votes becomes primary. Clients see a short window of write errors; drivers retry eligible writes once (retryable writes).
- Use an odd number of voting members (three is the usual minimum in production) so a majority can always form. Arbiters vote without data and are discouraged.
- Writes acknowledged with `w: "majority"` are never rolled back by an election.
- Even local development needs a (single-node) replica set if you use transactions or change streams. Atlas clusters are replica sets by default.

## 9. Sharding and shard key choice

Sharding splits one collection across several **shards** (each its own replica set), partitioned by a **shard key** field you choose. Applications connect to a router instead of a single replica set.

A good shard key has:
- **High cardinality** (many distinct values) so data can be split finely.
- **Even write distribution**: a monotonically increasing key (ObjectId, timestamp) with ranged sharding sends every insert to the last shard (a hot spot). Hashed sharding spreads writes but makes range queries scatter.
- **Query isolation**: most queries include the shard key, so they hit one shard (targeted) instead of all (scatter-gather).

For a multi-tenant app, a compound key like `{ storeId: 1, createdAt: 1 }` keeps a tenant's data together while still splitting large tenants. Newer versions can change a collection's shard key (resharding), but it is expensive: choose deliberately. Shard only when a well-indexed replica set on bigger hardware is no longer enough.

### Going deeper: how a sharded cluster routes queries
**mongos** routers receive every query and forward it to the right shards using cluster metadata stored on **config servers** (themselves a replica set). Data is divided into contiguous ranges of shard-key values (chunks), and a background balancer migrates chunks between shards to keep them even. A query that includes the shard key goes to one shard; one that does not is broadcast to all shards and merged by mongos, which is why query isolation matters so much.

## 10. Multi-document transactions

Single-document operations are always atomic, which covers most needs when related data is embedded. When a change must span documents or collections, use a transaction (replica sets since 4.0, sharded clusters since 4.2):

```ts
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    const res = await products.updateOne(
      { sku: "LAP-1", stock: { $gte: 1 } },       // conditional: never below zero
      { $inc: { stock: -1 } },
      { session }                                  // every operation must receive the session
    );
    if (res.modifiedCount === 0) throw new Error("Out of stock");   // aborts the transaction
    await orders.insertOne({ sku: "LAP-1", qty: 1, createdAt: new Date() }, { session });
  });
} finally {
  await session.endSession();
}
```

- `withTransaction` commits, aborts on errors and retries transient errors for you.
- Forgetting `{ session }` on one operation silently runs it outside the transaction.
- Transactions have a runtime limit (60 seconds by default), add overhead, and hold locks on the documents they write. Keep them short.
- Note the conditional update itself: for "decrement stock without overselling", the single-document `updateOne({ sku, stock: { $gte: 1 } }, { $inc: { stock: -1 } })` is atomic and needs no transaction.

## 12. The Node.js driver basics

```ts
import { MongoClient, ObjectId } from "mongodb";

type Order = {
  _id: ObjectId;
  storeId: ObjectId;
  status: "pending" | "paid" | "cancelled";
  totalCents: number;
  createdAt: Date;
};

const client = new MongoClient(process.env.MONGODB_URI!);   // create once per process: it owns a pool
const orders = client.db("shop").collection<Order>("orders");

export async function listPaidOrders(storeId: string) {
  if (!ObjectId.isValid(storeId)) throw new Error("Invalid store id");   // new ObjectId() throws otherwise
  return orders
    .find({ storeId: new ObjectId(storeId), status: "paid" }, { projection: { totalCents: 1, createdAt: 1 } })
    .sort({ createdAt: -1 })
    .limit(20)
    .toArray();
}

export async function markPaid(orderId: string) {
  const result = await orders.updateOne({ _id: new ObjectId(orderId) }, { $set: { status: "paid" } });
  return result.modifiedCount === 1;
}
```

- Recent driver versions connect automatically on the first operation; calling `await client.connect()` at startup is still fine and surfaces bad credentials early.
- In serverless and Next.js dev mode, modules are re-evaluated, so cache the client (or its connect promise) on `globalThis` to avoid opening a new pool per request; see [Mongoose connection caching](09-mongodb-schema-design-aggregation-mongoose.md) and [Next.js backend APIs and MongoDB](../07-nextjs-and-tanstack/03-nextjs-backend-apis-and-mongodb.md).
- `find` returns a cursor; `toArray()` loads everything, so always limit or stream large results.
- `findOneAndUpdate` accepts `returnDocument: "after"` to get the updated document; check your driver version for the result's exact shape.

## Common pitfalls
- Treating "schemaless" as "no schema": inconsistent field names and types across documents. Validate in the app (Zod, Mongoose) and with `$jsonSchema` for critical fields.
- Missing indexes: everything is a COLLSCAN until data grows, then the API slows down suddenly. Run `explain` on every hot query.
- Unbounded arrays (all comments or all log events inside one document) heading for the 16 MB limit and making every update rewrite a huge document.
- Using dot-notation conditions where `$elemMatch` was needed.
- Concurrent upserts without a unique index, creating duplicates.
- **NoSQL injection**: passing `req.body.email` straight into a filter lets an attacker send `{ "$ne": null }` and match any user. Validate input types (Zod), cast to strings, or enable Mongoose's `sanitizeFilter`.
- Creating a new `MongoClient` per request in serverless functions, exhausting Atlas connection limits.
- `skip`-based pagination on large collections.
- Forgetting `{ session }` on an operation inside a transaction.
- Reading from secondaries and being surprised by stale data right after a write.

## Interview questions

**Q1. What is MongoDB, and how does a document database differ from a relational one?**
MongoDB stores BSON documents in collections without a mandatory schema. Related data is often embedded in one document instead of normalized into tables, so a single read returns a whole aggregate, and single-document writes are atomic. There are no enforced foreign keys or traditional joins (only `$lookup`), so the schema is designed around the application's queries.

**Q2. When would you choose MongoDB over PostgreSQL, and when not?**
MongoDB for self-contained documents with varying fields read as a unit (catalogs, content, user profiles, event data), JSON-native stacks and horizontal write scaling. PostgreSQL when relationships are many-to-many and queried from every side, integrity rules must be enforced by the database, or the workload is report-heavy. Many teams pick Postgres by default and use JSONB for flexible parts.

**Q3. What is BSON, and what is inside an ObjectId?**
BSON is MongoDB's binary, typed, length-prefixed document format, with types JSON lacks (Date, ObjectId, Int64, Decimal128, Binary). An ObjectId is 12 bytes: a 4-byte timestamp, a 5-byte random value and a 3-byte incrementing counter, generated by the driver, so it is unique without coordination and roughly sorted by creation time.

**Q4. What is the difference between `$set` and `replaceOne`?**
`updateOne` with `$set` changes only the listed fields and leaves the rest. `replaceOne` replaces the entire document (keeping `_id`), so any field you omit is gone. Modern drivers reject an update document without operators to prevent accidental replacement; Mongoose adds `$set` automatically.

**Q5. How does an upsert work, and how can it create duplicates?**
With `upsert: true`, if no document matches the filter, MongoDB inserts one built from the filter's equality fields plus the update (`$setOnInsert` sets fields only on insert). Two concurrent upserts can both find nothing and both insert, unless a unique index on the filter fields makes the second one fail.

**Q6. What does `$elemMatch` do that dot notation does not?**
It requires a single array element to satisfy all the given conditions. Dot-notation conditions like `"items.sku"` and `"items.qty"` are evaluated independently, so different elements can satisfy each one, which returns false positives.

**Q7. Explain the ESR rule.**
Order compound index fields as Equality, then Sort, then Range. Equality fields narrow the scan to a contiguous section, the sort field then yields results in order without an in-memory sort, and the range field is filtered within that section. Example: `find({ storeId, status, total: { $gte: x } }).sort({ createdAt: -1 })` gets `{ storeId: 1, status: 1, createdAt: -1, total: 1 }`.

**Q8. What is a multikey index, and what are its limits?**
An index on an array field, with one index entry per array element, so queries like `{ tags: "sale" }` are fast. A compound index can contain at most one array field per document, and big arrays create many index entries, which slows writes.

**Q9. How do you use `explain()`, and what do you look for?**
Run `.explain("executionStats")` on the query. Check the winning plan for COLLSCAN (no index used) and SORT (in-memory sort), and compare `nReturned` with `totalKeysExamined` and `totalDocsExamined`; large ratios mean the index is a poor fit. A covered query examines zero documents.

**Q10. What is a TTL index used for?**
Automatically deleting documents after a time: set `expireAfterSeconds` on a Date field (or 0 with a per-document `expiresAt`). Typical uses: sessions, password-reset tokens, OTP codes, temporary carts, logs. A background task runs about once a minute, so deletion is approximate.

**Q11. What are write concern and read concern, and why use `w: "majority"`?**
Write concern decides when a write is acknowledged (primary only, or a majority of members, optionally journaled); read concern decides how durable the data a read returns must be. `w: "majority"` means the write survives a primary failover; with `w: 1` an acknowledged write can be rolled back after an election. It is the default in modern versions.

**Q12. How do replica sets and elections work?**
A primary takes writes and records them in the oplog; secondaries copy and apply it. When members lose contact with the primary for the election timeout, a secondary holding the most recent data can win a majority vote and become primary. Drivers discover the new primary and retry eligible writes. An odd number of voters keeps a majority possible.

**Q13. What is sharding, and how do you pick a shard key?**
Sharding partitions a collection across shards, with mongos routing queries by shard key. Pick a key with high cardinality, even write distribution (no monotonically increasing ranged keys) and presence in most queries so they target one shard. A compound key like `{ storeId, createdAt }` suits multi-tenant data. Changing it later is possible in newer versions but costly.

**Q14. Does MongoDB support transactions, and when do you use them?**
Yes: multi-document ACID transactions since 4.0 on replica sets and 4.2 on sharded clusters, through sessions (`withTransaction`). Use them when one business operation must change several documents atomically (moving money between two wallets). They cost more and have time limits, so prefer schemas where one document holds the invariant.

**Q15. How do you paginate efficiently?**
Range-based pagination: sort by an indexed, unique combination like `{ createdAt: -1, _id: -1 }` and ask for documents after the last seen values, with `limit`. `skip` makes the server walk past every skipped entry, so deep pages are slow and inserts shift results.

**Q16. What is NoSQL injection, and how do you prevent it?**
When user input is placed into a query filter unvalidated, an attacker can send an operator object, such as `{ "password": { "$ne": null } }`, changing the query's meaning (bypassing login checks). Prevent it by validating and casting input (Zod schemas, string coercion), never passing raw request bodies as filters, and enabling Mongoose's `sanitizeFilter`.

**Q17. Are single-document updates atomic? How would you prevent overselling?**
Yes. Every write to one document, including nested fields and arrays, is atomic. To avoid overselling, use a conditional update: `updateOne({ _id, stock: { $gte: qty } }, { $inc: { stock: -qty } })` and treat `modifiedCount === 0` as out of stock.

**Q18. Why reuse a single MongoClient?**
The client manages a connection pool, server discovery and monitoring. Creating one per request opens new connections every time (slow handshakes, TLS, authentication) and can exhaust the cluster's connection limit, especially in serverless functions. Create it once per process and cache it on `globalThis` where modules reload.
