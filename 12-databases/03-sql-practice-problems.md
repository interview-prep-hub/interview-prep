## Quick revision
- **Nth highest**: `DENSE_RANK() ... WHERE rnk = N`, or `DISTINCT ... ORDER BY ... OFFSET N-1 LIMIT 1` wrapped in a scalar subquery so "none" becomes NULL.
- **Top N per group**: rank inside a subquery with `PARTITION BY`, filter outside; or `CROSS JOIN LATERAL (... ORDER BY ... LIMIT N)`.
- **Latest row per group**: `DISTINCT ON (key) ... ORDER BY key, ts DESC` (Postgres) or `ROW_NUMBER() ... = 1` (portable).
- **No match** (never ordered, never sold): `NOT EXISTS` or `LEFT JOIN ... WHERE right.id IS NULL`. Not `NOT IN` on nullable columns.
- **Duplicates**: `GROUP BY key HAVING COUNT(*) > 1`; delete with `DELETE ... USING` self-join or `ROW_NUMBER() > 1`; then add a unique index.
- **Include empty groups**: drive from the parent table with LEFT JOIN, count a child column (`COUNT(e.id)`), `COALESCE(SUM(...), 0)`.
- **Ratios and growth**: `100.0 * x / NULLIF(y, 0)`; previous period with `LAG()`.
- **Running totals / moving averages**: `SUM() OVER (ORDER BY d ROWS ...)`; fill missing days with `generate_series` or use a `RANGE` interval frame.
- **Gaps and islands**: `date - ROW_NUMBER()` is constant within a streak.
- **Hierarchies**: `WITH RECURSIVE` (anchor `UNION ALL` recursive step).
- **Medians**: `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)`.
- **Pivot**: `COUNT(*) FILTER (WHERE ...)` or `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.
- Aggregate to the right grain before averaging (order totals first, then average them).

## 2. Ranking and top N

### P1. Second highest salary (LeetCode 176)
**Problem:** return the second highest distinct salary, or NULL if there is none.
```sql
-- A) OFFSET, wrapped in a scalar subquery so "no row" becomes NULL
SELECT (SELECT DISTINCT salary FROM employees
        ORDER BY salary DESC OFFSET 1 LIMIT 1) AS second_highest;

-- B) The max below the max
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- C) DENSE_RANK (generalizes to any N)
SELECT DISTINCT salary AS second_highest
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees) t
WHERE rnk = 2;
```
**Why:** `DISTINCT`/`DENSE_RANK` make two people sharing the top salary count once. B is the most portable. Result: 195000.
**ActiveRecord:**
```ruby
Employee.distinct.order(salary: :desc).offset(1).pick(:salary)          # one query
Employee.where("salary < ?", Employee.maximum(:salary)).maximum(:salary)  # two queries
```

### P2. Nth highest salary (LeetCode 177)
```sql
CREATE OR REPLACE FUNCTION nth_highest_salary(n integer) RETURNS numeric AS $$
  SELECT DISTINCT salary FROM employees
  ORDER BY salary DESC
  OFFSET n - 1 LIMIT 1;            -- a scalar SQL function returns NULL when no row comes back
$$ LANGUAGE sql STABLE;

SELECT nth_highest_salary(3);      -- 180000

-- Classic correlated version: exactly N-1 distinct salaries are higher (O(n^2), but portable)
SELECT DISTINCT salary FROM employees e1
WHERE 2 = (SELECT COUNT(DISTINCT salary) FROM employees e2 WHERE e2.salary > e1.salary);
```
**Why:** same idea as P1 with a parameter. Mention input validation (N < 1) if asked.

### P3. Highest-paid employee in each department (LeetCode 184)
```sql
SELECT department, name, salary
FROM (
  SELECT d.name AS department, e.name, e.salary,
         RANK() OVER (PARTITION BY e.department_id ORDER BY e.salary DESC) AS rnk
  FROM employees e
  JOIN departments d ON d.id = e.department_id
) t
WHERE rnk = 1;
```
**Why:** `RANK` keeps ties. The correlated alternative is `WHERE e.salary = (SELECT MAX(salary) FROM employees x WHERE x.department_id = e.department_id)`. Result: Engineering/Ayesha 250000, Sales/Zara 150000, Marketing/Fatima 120000.

### P4. Top 2 earners per department (top N per group; LeetCode 185 uses top 3)
```sql
SELECT department_id, name, salary
FROM (
  SELECT department_id, name, salary,
         DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employees
  WHERE department_id IS NOT NULL            -- otherwise NULLs form their own partition
) ranked
WHERE rnk <= 2
ORDER BY department_id, salary DESC;

-- LATERAL: "for each department, its top 2" (fast with an index on (department_id, salary))
SELECT d.name, top.name, top.salary
FROM departments d
CROSS JOIN LATERAL (
  SELECT e.name, e.salary FROM employees e
  WHERE e.department_id = d.id
  ORDER BY e.salary DESC
  LIMIT 2
) top;
```
**Why:** with `DENSE_RANK`, Sales returns three people (Usman and Hira tie at 90000); switch to `ROW_NUMBER` for exactly two. Window functions cannot go in WHERE, hence the subquery.
**ActiveRecord:**
```ruby
ranked = Employee.where.not(department_id: nil)
                 .select("employees.*, DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk")
Employee.from(ranked, :employees).where("rnk <= 2")
```

### P5. Rank products by revenue within each category
```sql
WITH product_revenue AS (
  SELECT p.category_id, p.name, SUM(oi.quantity * oi.unit_price) AS revenue
  FROM products p
  JOIN order_items oi ON oi.product_id = p.id
  JOIN orders o ON o.id = oi.order_id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY p.id, p.category_id, p.name
)
SELECT c.name AS category, pr.name AS product, pr.revenue,
       RANK() OVER (PARTITION BY pr.category_id ORDER BY pr.revenue DESC) AS rank_in_category
FROM product_revenue pr
JOIN categories c ON c.id = pr.category_id
ORDER BY category, rank_in_category;
```
**Why:** aggregate first (CTE), then rank the aggregates. Result: Electronics: Laptop 2350 (1), Monitor 1200 (2); Accessories: Keyboard 180, Mouse 175; Board Games: Catan 150, Chess Set 90; Books: SQL Book 200.

### P6. Top 3 customers by total spend, ties included
```sql
SELECT name, spent
FROM (
  SELECT c.name, SUM(oi.quantity * oi.unit_price) AS spent,
         DENSE_RANK() OVER (ORDER BY SUM(oi.quantity * oi.unit_price) DESC) AS rnk
  FROM customers c
  JOIN orders o ON o.customer_id = c.id AND o.status IN ('paid', 'shipped')
  JOIN order_items oi ON oi.order_id = o.id
  GROUP BY c.id, c.name
) t
WHERE rnk <= 3;
```
**Why:** a window function can wrap an aggregate because windows run after GROUP BY. Postgres 13+ also offers `ORDER BY spent DESC FETCH FIRST 3 ROWS WITH TIES`. Result: Ahmed 1810, Maryam 1520, Imran 800.

## 3. Self joins and anti-joins

### P7. Employees who earn more than their manager (LeetCode 181)
```sql
SELECT e.name AS employee, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;
```
**Why:** a self join under two aliases. INNER JOIN naturally drops the CEO. Result: Hamza (195000 vs Bilal 180000), Fatima (120000 vs Omar 110000).
**ActiveRecord:**
```ruby
Employee.joins("JOIN employees managers ON managers.id = employees.manager_id")
        .where("employees.salary > managers.salary")
        .pluck("employees.name", "managers.name")
```

### P8. Managers with at least two direct reports (LeetCode 570 uses five)
```sql
SELECT m.name, COUNT(*) AS direct_reports
FROM employees e
JOIN employees m ON m.id = e.manager_id
GROUP BY m.id, m.name
HAVING COUNT(*) >= 2
ORDER BY direct_reports DESC;
```
Result: Ayesha 4, Bilal 2, Zara 2. Group by `m.id`, not just the name, because names are not unique.

### P9. Departments with no employees
```sql
SELECT d.name
FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.department_id = d.id);
```
Result: Support. The `LEFT JOIN employees e ... WHERE e.id IS NULL` form is equivalent.

### P10. Customers who never ordered (LeetCode 183)
```sql
-- A) NOT EXISTS: NULL-safe and states the intent
SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- B) LEFT JOIN anti-join
SELECT c.name FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- C) NOT IN: correct here only because orders.customer_id is NOT NULL
SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);
```
**Why:** if the subquery column could contain NULL, C would return nothing (see [NULL logic](02-sql-from-zero.md)). Result: Saad, Amna.
**ActiveRecord:**
```ruby
Customer.where.missing(:orders)                          # Rails 6.1+: LEFT JOIN ... WHERE orders.id IS NULL
Customer.left_joins(:orders).where(orders: { id: nil })  # same SQL on older Rails
Customer.where.not(id: Order.select(:customer_id))       # NOT IN (subquery)
```

### P11. Products never sold
```sql
SELECT p.name
FROM products p
WHERE NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.product_id = p.id);
```
Result: Headphones. For "never sold in a paid order", join `orders` inside the subquery and filter its status.

### P12. Customers who bought both Laptop and Mouse, and Laptop but not Mouse
```sql
-- Both: count the distinct matching products per customer
SELECT o.customer_id
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.status IN ('paid', 'shipped') AND p.name IN ('Laptop', 'Mouse')
GROUP BY o.customer_id
HAVING COUNT(DISTINCT p.name) = 2;

-- Laptop but not Mouse: boolean aggregates per customer
SELECT o.customer_id
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.status IN ('paid', 'shipped')
GROUP BY o.customer_id
HAVING bool_or(p.name = 'Laptop') AND NOT bool_or(p.name = 'Mouse');
```
**Why:** `INTERSECT` / `EXCEPT` of two customer-id queries also work. Result: both = customer 1 (Ahmed); Laptop without Mouse = customer 2 (Maryam).

## 4. Duplicates

### P13. Find duplicate emails (LeetCode 182)
```sql
SELECT email, COUNT(*) AS copies
FROM leads
GROUP BY email
HAVING COUNT(*) > 1;
```
Result: sara@example.com 3, ali@example.com 2. For case-insensitive duplicates, group by `lower(email)`.
**ActiveRecord:**
```ruby
Lead.group(:email).having("COUNT(*) > 1").count   # Hash of email => copies
```

### P14. Delete duplicates, keeping the lowest id (LeetCode 196)
```sql
-- A) Self-join delete: remove any row that has a twin with a smaller id
DELETE FROM leads a
USING leads b
WHERE a.email = b.email AND a.id > b.id;

-- B) ROW_NUMBER: flexible (ORDER BY created_at DESC keeps the newest instead)
DELETE FROM leads
WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM leads
  ) t
  WHERE rn > 1
);

-- Then make it impossible to happen again
CREATE UNIQUE INDEX leads_email_unique ON leads (lower(email));
```
**Why:** run the inner SELECT first to preview what goes. Ids 3, 5 and 6 are deleted. MySQL refuses a subquery on the table being deleted from (error 1093); wrap it in a derived table there.
**ActiveRecord:**
```ruby
Lead.where.not(id: Lead.group(:email).select("MIN(id)")).delete_all   # one DELETE ... NOT IN (subquery)
```

## 5. Aggregation

### P15. Headcount and average salary per department, including empty ones
```sql
SELECT d.name, COUNT(e.id) AS headcount, ROUND(AVG(e.salary), 2) AS avg_salary
FROM departments d
LEFT JOIN employees e ON e.department_id = d.id
GROUP BY d.id, d.name
ORDER BY d.id;
```
**Why:** `COUNT(*)` would report 1 for Support (the NULL-extended row); `COUNT(e.id)` reports 0. Result: Engineering 4 / 186250.00, Sales 3 / 110000.00, Marketing 2 / 115000.00, Support 0 / NULL.

### P16. Orders whose total exceeds 500
```sql
SELECT o.id, SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status IN ('paid', 'shipped')          -- row filter
GROUP BY o.id
HAVING SUM(oi.quantity * oi.unit_price) > 500  -- group filter
ORDER BY total DESC;
```
Result: order 1 (1250), order 10 (1150), order 4 (600). Cancelled order 6 (1200) is removed by WHERE before grouping.

### P17. Average order value (AOV) per customer
```sql
WITH order_totals AS (
  SELECT o.id, o.customer_id, SUM(oi.quantity * oi.unit_price) AS total
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY o.id, o.customer_id
)
SELECT c.name, COUNT(*) AS orders, SUM(t.total) AS spent, ROUND(AVG(t.total), 2) AS aov
FROM order_totals t
JOIN customers c ON c.id = t.customer_id
GROUP BY c.id, c.name
ORDER BY aov DESC;
```
**Why:** the classic bug is `AVG(oi.quantity * oi.unit_price)`, which averages line items (Ahmed would show 201.11 instead of 362.00). Get to order grain first. Result: Maryam 506.67, Ahmed 362.00, Imran 266.67, Noor 107.50.

### P18. Revenue per category, including categories with no sales
```sql
SELECT c.name AS category, COALESCE(SUM(s.revenue), 0) AS revenue
FROM categories c
LEFT JOIN products p ON p.category_id = c.id
LEFT JOIN (
  SELECT oi.product_id, SUM(oi.quantity * oi.unit_price) AS revenue
  FROM order_items oi
  JOIN orders o ON o.id = oi.order_id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY oi.product_id
) s ON s.product_id = p.id
GROUP BY c.id, c.name
ORDER BY revenue DESC;
```
**Why:** filtering `orders` in an outer WHERE would delete the zero rows; doing the inner join and filter in a subquery keeps the LEFT JOINs intact (P19 shows the `FILTER` alternative). Result: Electronics 3550, Accessories 355, Board Games 240, Books 200, Games 0 (its products sit in the child category; P36 rolls them up).
**ActiveRecord:**
```ruby
Category.joins(products: { order_items: :order })
        .where(orders: { status: %w[paid shipped] })
        .group("categories.name")
        .sum("order_items.quantity * order_items.unit_price")
# INNER joins: categories without sales are absent, so default missing names to 0 in Ruby
```

### P19. Each category's percentage of total revenue
```sql
WITH category_revenue AS (
  SELECT c.name AS category,
         COALESCE(SUM(oi.quantity * oi.unit_price)
                  FILTER (WHERE o.status IN ('paid', 'shipped')), 0) AS revenue
  FROM categories c
  LEFT JOIN products p     ON p.category_id = c.id
  LEFT JOIN order_items oi ON oi.product_id = p.id
  LEFT JOIN orders o       ON o.id = oi.order_id
  GROUP BY c.id, c.name
)
SELECT category, revenue,
       ROUND(100.0 * revenue / NULLIF(SUM(revenue) OVER (), 0), 2) AS pct_of_total
FROM category_revenue
ORDER BY revenue DESC;
```
**Why:** `SUM(revenue) OVER ()` (an empty window) is the grand total on every row, so no second query. Result: Electronics 81.70, Accessories 8.17, Board Games 5.52, Books 4.60, Games 0.00.

### P20. Pivot: order counts per month by status
```sql
SELECT to_char(ordered_at, 'YYYY-MM') AS month,
       COUNT(*) FILTER (WHERE status = 'paid')      AS paid,
       COUNT(*) FILTER (WHERE status = 'shipped')   AS shipped,
       COUNT(*) FILTER (WHERE status = 'pending')   AS pending,
       COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled
FROM orders
GROUP BY 1
ORDER BY 1;
-- Portable form (MySQL too): SUM(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid
```

### P21. Median and percentiles of order value
```sql
WITH order_totals AS (
  SELECT o.id, SUM(oi.quantity * oi.unit_price) AS total
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY o.id
)
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY total) AS median,       -- interpolates
       percentile_disc(0.5) WITHIN GROUP (ORDER BY total) AS median_disc,  -- an actual value
       percentile_cont(0.9) WITHIN GROUP (ORDER BY total) AS p90,
       ROUND(AVG(total), 2) AS mean
FROM order_totals;
```
**Why:** ordered-set aggregates. Result over 13 orders: median 125, p90 1040 (between 600 and 1150), mean 334.23. The gap between mean and median shows the skew from laptop orders, which is why dashboards report medians and p90s.

### P22. Products priced above their category's average
```sql
SELECT p.name, p.price, ROUND(cat.avg_price, 2) AS category_avg
FROM products p
JOIN (SELECT category_id, AVG(price) AS avg_price FROM products GROUP BY category_id) cat
  ON cat.category_id = p.category_id
WHERE p.price > cat.avg_price;
```
Result: Laptop (1200 vs 750), Headphones (80 vs 50), Catan (50 vs 40).

### P23. Employees earning above their department's average
```sql
SELECT name, department_id, salary, ROUND(dept_avg, 2) AS dept_avg
FROM (
  SELECT name, department_id, salary,
         AVG(salary) OVER (PARTITION BY department_id) AS dept_avg
  FROM employees
) t
WHERE salary > dept_avg;
```
**Why:** one pass instead of a correlated subquery per row. Result: Ayesha and Hamza (Engineering avg 186250), Zara (Sales 110000), Fatima (Marketing 115000).

## 6. Latest and previous rows

### P24. Latest order per customer
```sql
-- Postgres: DISTINCT ON keeps the first row per customer_id by the ORDER BY
SELECT DISTINCT ON (customer_id) customer_id, id AS order_id, ordered_at
FROM orders
ORDER BY customer_id, ordered_at DESC, id DESC;

-- Portable: ROW_NUMBER
SELECT customer_id, id AS order_id, ordered_at
FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_at DESC, id DESC) AS rn
  FROM orders o
) t
WHERE rn = 1;
```
**Why:** `DISTINCT ON` requires ORDER BY to start with the same expressions; the `id` tie-breaker makes the pick deterministic. An index on `(customer_id, ordered_at DESC)` serves both. Result: customer 1 -> order 13, 2 -> 14, 3 -> 15, 4 -> 12.
**ActiveRecord:**
```ruby
Order.select("DISTINCT ON (customer_id) orders.*")
     .order(:customer_id, ordered_at: :desc, id: :desc)
```

### P25. Second most recent order per customer
```sql
SELECT customer_id, id AS order_id, ordered_at
FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_at DESC) AS rn
  FROM orders o
) t
WHERE rn = 2;
```
Result: customer 1 -> order 11, 2 -> 10, 3 -> 9, 4 -> 7. Customers with one order simply do not appear.

### P26. Days between consecutive orders
```sql
SELECT customer_id, id, ordered_at::date AS day,
       ordered_at::date - LAG(ordered_at::date)
         OVER (PARTITION BY customer_id ORDER BY ordered_at) AS days_since_previous
FROM orders
ORDER BY customer_id, ordered_at;
```
**Why:** `date - date` is an integer number of days. For customer 1: NULL, 24, 26, 37, 51, 13. Wrap it and `AVG(days_since_previous)` for the average purchase interval (30.2 days).

## 7. Time series

### P27. Daily revenue with a running total
```sql
WITH daily AS (
  SELECT o.ordered_at::date AS day, SUM(oi.quantity * oi.unit_price) AS revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY 1
)
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM daily
ORDER BY day;
```
**Why:** add `PARTITION BY date_trunc('month', day)` for month-to-date totals. Result: starts at 2025-01-10 with 1250 and ends at 2025-06-15 with 4345.

### P28. Rolling 7-day average revenue, with missing days filled
```sql
WITH daily AS (
  SELECT o.ordered_at::date AS day, SUM(oi.quantity * oi.unit_price) AS revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY 1
),
calendar AS (
  SELECT d::date AS day
  FROM generate_series('2025-06-01'::date, '2025-06-30'::date, interval '1 day') AS d
)
SELECT c.day,
       COALESCE(d.revenue, 0) AS revenue,
       ROUND(AVG(COALESCE(d.revenue, 0))
             OVER (ORDER BY c.day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS avg_7d
FROM calendar c
LEFT JOIN daily d ON d.day = c.day
ORDER BY c.day;
```
**Why:** `ROWS 6 PRECEDING` over the sparse `daily` table would average the last seven days that had sales, not the last seven calendar days. Either fill the calendar (above) or, on `daily`, use `SUM(revenue) OVER (ORDER BY day RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW) / 7.0`. For 2025-06-15 the calendar average is 645 / 7 = 92.14; averaging only the four days with sales would wrongly give 161.25. The first six calendar days average fewer than seven rows; start the series earlier if that matters.

### P29. Month-over-month revenue growth
```sql
WITH monthly AS (
  SELECT date_trunc('month', o.ordered_at)::date AS month,
         SUM(oi.quantity * oi.unit_price) AS revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped')
  GROUP BY 1
)
SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 2) AS growth_pct
FROM monthly
ORDER BY month;
```

| month | revenue | prev_revenue | growth_pct |
|---|---|---|---|
| 2025-01-01 | 1320 | NULL | NULL |
| 2025-02-01 | 670 | 1320 | -49.24 |
| 2025-03-01 | 175 | 670 | -73.88 |
| 2025-04-01 | 385 | 175 | 120.00 |
| 2025-05-01 | 1150 | 385 | 198.70 |
| 2025-06-01 | 645 | 1150 | -43.91 |

**Why:** a month with no sales would be missing, and LAG would silently compare with two months back; fill months with `generate_series` when that can happen. Year over year is `LAG(revenue, 12)`.

### P30. Customers active in every month from January to June 2025
```sql
SELECT customer_id
FROM orders
WHERE status <> 'cancelled'
  AND ordered_at >= '2025-01-01' AND ordered_at < '2025-07-01'
GROUP BY customer_id
HAVING COUNT(DISTINCT date_trunc('month', ordered_at)) = 6;
```
**Why:** count distinct months per customer and compare with the number of months in the range (compute it with `generate_series` instead of hardcoding 6 in real code). Result: customer 1 (Ahmed).

### P31. New customers per month (cohort by first order)
```sql
WITH first_orders AS (
  SELECT customer_id, MIN(ordered_at) AS first_ordered_at
  FROM orders
  GROUP BY customer_id

SELECT date_trunc('month', first_ordered_at)::date AS cohort_month, COUNT(*) AS new_customers
FROM first_orders
GROUP BY 1
ORDER BY 1;
```
Result: 2025-01: 2, 2025-02: 1, 2025-03: 1. "Returning customers per month" is active customers minus new ones.

### P32. Longest consecutive-day login streak (gaps and islands)
```sql
WITH grouped AS (
  SELECT customer_id, login_date,
         login_date - (ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY login_date))::int AS grp
  FROM logins
),
streaks AS (
  SELECT customer_id, MIN(login_date) AS start_date, MAX(login_date) AS end_date, COUNT(*) AS days
  FROM grouped
  GROUP BY customer_id, grp
)
SELECT DISTINCT ON (customer_id) customer_id, start_date, end_date, days
FROM streaks
ORDER BY customer_id, days DESC;
```
**Why:** inside a run of consecutive dates, the date and its row number both grow by 1, so `date - row_number` stays constant and labels the island:

| login_date (customer 2) | row_number | date - row_number |
|---|---|---|
| 2025-06-01 | 1 | 2025-05-31 |
| 2025-06-03 | 2 | 2025-06-01 |
| 2025-06-04 | 3 | 2025-06-01 |
| 2025-06-05 | 4 | 2025-06-01 |
| 2025-06-06 | 5 | 2025-06-01 |

Result: customer 1: 3 days (06-01 to 06-03), customer 2: 4 days (06-03 to 06-06), customer 3: 1 day. Deduplicate first if the source can hold several rows per day. LeetCode 180 and 601 are variants of this pattern.

### P33. The day (or days) with the highest revenue

## 8. Hierarchies

### P34. Org chart with a recursive CTE
```sql
WITH RECURSIVE org AS (
  SELECT id, name, 0 AS depth, ARRAY[name] AS path
  FROM employees
  WHERE manager_id IS NULL                   -- anchor: the top of the tree
  UNION ALL
  SELECT e.id, e.name, org.depth + 1, org.path || e.name
  FROM employees e
  JOIN org ON e.manager_id = org.id          -- step: direct reports of the previous level
)
SELECT repeat('  ', depth) || name AS org_chart, depth
FROM org
ORDER BY path;                               -- array ordering gives depth-first output
```

### P35. Chain of command for one employee (walking up)
```sql
WITH RECURSIVE chain AS (
  SELECT id, name, manager_id, 0 AS level FROM employees WHERE name = 'Fatima'
  UNION ALL
  SELECT m.id, m.name, m.manager_id, chain.level + 1
  FROM employees m
  JOIN chain ON m.id = chain.manager_id
)
SELECT level, name FROM chain ORDER BY level;
```
Result: Fatima (0), Omar (1), Ayesha (2). Add `WHERE chain.level < 50` in the step if bad data could contain a cycle.

### P36. Revenue rolled up to top-level categories
```sql
WITH RECURSIVE tree AS (
  SELECT id, id AS root_id FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, tree.root_id FROM categories c JOIN tree ON c.parent_id = tree.id
)
SELECT r.name AS top_category,
       COALESCE(SUM(oi.quantity * oi.unit_price)
                FILTER (WHERE o.status IN ('paid', 'shipped')), 0) AS revenue
FROM tree t
JOIN categories r        ON r.id = t.root_id
LEFT JOIN products p     ON p.category_id = t.id
LEFT JOIN order_items oi ON oi.product_id = p.id
LEFT JOIN orders o       ON o.id = oi.order_id
GROUP BY r.id, r.name
ORDER BY revenue DESC;
```
**Why:** the CTE maps every category to its root, then a normal aggregation sums by root. Result: Electronics 3905 (includes Accessories), Games 240 (Board Games), Books 200.

## 9. Changing data

### P37. Swap values in a single UPDATE
```sql
BEGIN;
-- Swap two statuses (LeetCode 627 swaps two values the same way)
UPDATE orders
SET status = CASE status WHEN 'paid' THEN 'shipped' ELSE 'paid' END
WHERE status IN ('paid', 'shipped');

-- Swap the salaries of employees 2 and 4: the FROM side reads the pre-update values
UPDATE employees e
SET salary = o.salary
FROM employees o
WHERE (e.id, o.id) IN ((2, 4), (4, 2));
ROLLBACK;
```
**Why:** one statement, so there is no intermediate state. In Postgres `SET a = b, b = a` also swaps two columns, because every right-hand side sees the old row; MySQL assigns left to right, so both columns end up equal there.

### P38. Give a 10% raise to everyone below their department's average
```sql
BEGIN;
UPDATE employees e
SET salary = ROUND(e.salary * 1.10, 2)
FROM (SELECT department_id, AVG(salary) AS avg_salary
      FROM employees GROUP BY department_id) d
WHERE d.department_id = e.department_id
  AND e.salary < d.avg_salary
RETURNING e.name, e.salary;
ROLLBACK;   -- keep the practice data unchanged
```
**Why:** averages are computed once from the pre-update snapshot, so earlier raises do not shift the threshold. Bilal, Sana, Usman, Hira and Omar get raises; Ali (NULL department) never matches `=`.

### P39. Employees hired in 2024, written so an index can help
```sql
-- Index-friendly: half-open range on the raw column
SELECT name, hired_on FROM employees
WHERE hired_on >= '2024-01-01' AND hired_on < '2025-01-01';

-- Same rows, but a plain index on hired_on cannot be used
SELECT name, hired_on FROM employees WHERE extract(year FROM hired_on) = 2024;
```
Result: Fatima, Ali. Wrapping the column in a function makes the predicate non-sargable ([indexing](05-indexing-and-query-optimization.md)).

### P40. Find gaps in an id sequence
```sql
-- Every missing id
SELECT s.id AS missing_id
FROM generate_series(1, (SELECT MAX(id) FROM leads)) AS s(id)
WHERE NOT EXISTS (SELECT 1 FROM leads l WHERE l.id = s.id);

-- Or report each gap as a range
SELECT id + 1 AS gap_start, next_id - 1 AS gap_end
FROM (SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM leads) t
WHERE next_id - id > 1;
```
Result after running P14: id 3 is missing. Gaps in identity columns are normal (rolled-back inserts consume values), so never use ids as a gap-free invoice sequence.

## Common pitfalls
- Answering before clarifying ties, NULLs and which statuses count. Most "wrong" answers are right answers to a different question.
- Averaging at the wrong grain (line items instead of orders), or summing after joining two child tables, which multiplies rows.
- `LIMIT 1` for "the highest", silently dropping ties.
- `COUNT(*)` with a LEFT JOIN, which counts the NULL-extended row as 1.
- Filtering the right side of a LEFT JOIN in WHERE, losing the zero rows you were asked to show.
- `NOT IN` against a nullable column.
- Window functions in WHERE (not allowed); wrap them in a subquery or CTE.
- Time series with missing days or months: LAG and ROWS frames assume rows are consecutive periods.
- Running destructive practice queries (P14, P37, P38) outside `BEGIN ... ROLLBACK`.
- Forgetting deterministic tie-breakers (`ORDER BY ordered_at DESC, id DESC`) so results differ between runs.

- From assisting in the Databases lab at PUCIT you know the classic student bugs (NOT IN with NULL, wrong grain, missing GROUP BY columns); naming them before they bite impresses interviewers.

## Interview questions

**Q1. How do you approach a SQL question in a live interview?**
Restate the problem, ask about ties, NULLs, duplicates and date boundaries, and look at the schema. Write FROM/JOIN first, then WHERE, GROUP BY, HAVING, SELECT, ORDER BY. Build in steps with CTEs, sanity-check intermediate results against a few rows by hand, and finish by naming edge cases and the indexes the query would want.

**Q2. What clarifying questions do you ask before writing the query?**
Do ties count? Should entities with zero activity appear? Which statuses count (is a cancelled or pending order revenue)? Are dates inclusive, and in which time zone? Can the key columns be NULL or duplicated? How large are the tables (is a correlated subquery acceptable)?

**Q3. How do you handle ties in "top N" questions?**
Ask first. `ROW_NUMBER` returns exactly N rows (add a deterministic tie-breaker), `RANK` returns everyone tied at the boundary with gaps, `DENSE_RANK` returns the top N distinct values. In Postgres 13+, `FETCH FIRST N ROWS WITH TIES` does the RANK-style version with plain ORDER BY.

**Q4. Your query returns more rows than expected. How do you debug it?**
Look for join fan-out: a one-to-many join multiplies parent rows, and two one-to-many joins multiply each other. Check each join's cardinality with `COUNT(*)` step by step, confirm every join has its full condition, and aggregate child tables in subqueries before joining them.
*Follow-up:* And fewer rows than expected? Usually an INNER JOIN that should be LEFT, a WHERE on the right side of a LEFT JOIN, or NULLs failing a comparison.

**Q5. When do you choose a window function over GROUP BY or a subquery?**
When you need per-row detail plus a group-level value: rank within group, running total, previous row, share of total, department average next to each salary. GROUP BY when you want one row per group. Window functions also replace many correlated subqueries with a single pass.

**Q6. DISTINCT ON or ROW_NUMBER for "latest row per group"?**
`DISTINCT ON` is shorter and fast in Postgres but Postgres-only and limited to one row per group. `ROW_NUMBER` is portable (MySQL 8, SQL Server) and generalizes to "second latest" or "latest 3". On very large tables with an index on `(group_key, ts DESC)`, a LATERAL subquery with `LIMIT 1` per group can be fastest.

**Q7. How would you make one of these queries fast on 100 million rows?**
Run `EXPLAIN (ANALYZE, BUFFERS)`, then add indexes that match the filters and sort (for example `(customer_id, ordered_at DESC)` for latest-per-customer), make predicates sargable, select fewer columns, and pre-aggregate into rollup tables or materialized views for dashboards. See [indexing](05-indexing-and-query-optimization.md).

**Q8. How do you translate a Postgres answer to MySQL?**
MySQL 8 has CTEs and window functions, so most answers port directly. Replace `DISTINCT ON` with `ROW_NUMBER`, `FILTER (WHERE ...)` with `SUM(CASE ...)`, `ILIKE` with `LIKE` (case-insensitive under the default collation), `generate_series` with a recursive CTE, and `DELETE ... USING` with a multi-table `DELETE a FROM leads a JOIN leads b ...`. See [MySQL essentials](07-mysql-essentials.md).

**Q9. Explain the gaps-and-islands technique.**
Number the rows in order within each group; for consecutive values the value minus its row number is constant, so grouping by that difference collects each consecutive run into one group. Then `MIN`, `MAX` and `COUNT` give each streak's start, end and length. It works for dates, integers and sequences of statuses (with a second ROW_NUMBER per status).

**Q10. How do you avoid double counting when a query touches several one-to-many tables?**
Aggregate each child table to the parent's grain in its own subquery or CTE (order totals, payment totals), then join those one-row-per-parent results. Never sum a column from one child after joining another child.

**Q11. How do you test a query when you cannot run it?**
Walk through two or three representative rows by hand, including an edge row (a customer with no orders, a NULL department, a tie). Check the output grain ("one row per what?") and whether every non-aggregated column is in GROUP BY.

**Q12. How would you write these in ActiveRecord, and when would you just use SQL?**
Simple ones map cleanly: `where.missing`, `group(...).having(...).count`, `joins(...).sum(...)`, `pick`. Window functions and DISTINCT ON fit through `select` strings and `from(subquery, alias)`. For multi-step reports, `find_by_sql` or a database view backed by a read-only model is clearer than a chain of string fragments. Always pass user input as bind parameters.

**Q13. The interviewer says "what if the table has duplicates?" What changes?**
Decide whether duplicates are exact copies or same-key rows, then dedupe before aggregating (`SELECT DISTINCT` or `ROW_NUMBER() ... = 1` in a CTE). Then suggest fixing the source with a unique constraint, because every query working around duplicates is a future bug.

**Q14. Why do ids have gaps, and does it matter?**
Sequences and identity columns hand out values outside transaction control, so rolled-back inserts, failed upserts and cached sequence values leave gaps. That is fine for surrogate keys. For gap-free numbering (invoice numbers), use a separate counter row updated under a lock inside the transaction.
